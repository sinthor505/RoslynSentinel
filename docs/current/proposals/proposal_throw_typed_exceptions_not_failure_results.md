## Motivation

Failure is carried today in two parallel ways, and the second one is where errors slip through.

1. **Typed throws** (`ToolException` family, 103 `ToolNotFoundException` sites alone): loud and unambiguous.
2. **Outcome / nullable results**: `DocumentEditResult` has nullable `[JsonIgnore] UpdatedText`, `Outcome` (`EditOutcome`, 15 values), `Message`, `ErrorCode`, `Candidates` (`Common/DocumentEditResult.cs:22`). Every layer must check, parse and interpret these.

Measured spread of the second carrier (non-test code, from the 2026-10-20 survey):
- 148 engine methods return `Task<DocumentEditResult>` across 24 files (`MemberRefactoringEngine` 32, `BasicRefactoringEngine` 15, `AdvancedStructuralEngine` 12, `LogicOptimizationEngine` 12, `SyntaxUpgradeEngine` 11, `AsyncOptimizationEngine` 10, `ModernizationEngine` 9).
- 767 `EditOutcome.X` references in 37 files; 87 explicit `UpdatedText` null/empty checks in 12 files (tools ~76, engines ~11); ~35 explicit `EditOutcome` consumer sites; 18 external `RequireUpdatedText` and 19 `GuardEngineResult` call sites.
- The round trip: 36 engine `catch (ToolException)` sites (6 files; `MemberRefactoringEngine` 28; recounted 2026-10-21, the first survey said ~71) convert the exception back into a `DocumentEditResult` (`Outcome = CannotEdit`, `Message = ex.Message`, `ErrorCode = ex.ErrorCode`), and a tool-layer guard then rebuilds a `ResultError` from that (`RefactoringToolHelpers.cs:38`, `:65-89`, `:130`). Only 2 of those sites copy `Candidates`; 30 copy `ErrorCode`; the rest lose the category.
- Known slip-throughs: ~50 consumers map empty `UpdatedText` to success and can mask an `Error` outcome (plan_error_codes_follow_cause Re-baseline); 34 File/Class-scope sites in `CodeTransformTools` do this today; `SummarizeEngineMessage` keeps only the first non-blank line (`RefactoringToolHelpers.cs:209-219`), truncating multi-line snippet failures on the guard path.
- The 2026-10-20 test audit (`findings/20261020-Comprehensive-Review_Tests.*.md`) found ~650 weak tests; the dominant mechanisms are exactly this design: `UpdatedText Is.Null` standing in for "not found", `Is.Not.Null` on a never-null DTO, and engines returning `Modified` on a no-op. Where failures already throw (MoveMember, `EngineResultWrapper.Data`), the tests were consistently strong.

## Proposal

### 1. Principle (decided direction)
- **Throw** when the request cannot be honoured: document not found, target not found, snippet did not match, ambiguous match, target ineligible, invalid argument, feature disabled, refused as unsafe, diff failed.
- **Return a result** when nothing is wrong: `Modified`, `AlreadyInTargetState` (the only no-op outcome; `NoChange` is eliminated, see open question 1), detectors that find nothing, zero-match searches (see `plans/plan_zero_match_is_not_an_error.md`: empty valid answers stay successes).
- **Batch and scan engines keep per-item results** (`ItemFailure`, `BatchResultSummary`, `ApplyChangesResult.FailedFiles`): a throw would abort the remaining items. Single-target operations throw; per-item loops catch and record.
- Success types become non-nullable: `DocumentEditResult.UpdatedText` is a required `string`; a snippet resolver returns a match or throws, never a nullable match.

### 2. Can exceptions carry the rich engine data? Yes, with payload added
The repo already has the family (all in `RoslynSentinel.Common` unless noted): abstract `ToolException` (abstract `ErrorCode`, `ToolException.cs:13`) and `SolutionNotLoadedException`, `SolutionLoadTimeoutException`, `ToolNotFoundException`, `ToolInvalidArgumentException`, `ToolAmbiguousMatchException`, `ToolTargetIneligibleException`, `DiffApplyException`, `ToolNotImplementedException`, `SessionHaltedException`, `GlobSyntaxException`, plus `ToolMatchedLooserTierException` (`SnippetMatching/SnippetErrorFormatter.cs:14`). So the mechanism exists and works.

What is missing is payload. Today every type carries only a message except `ToolAmbiguousMatchException`, which has `IReadOnlyList<AmbiguousCandidate>? Candidates`. The rich data now flattens into message text: `SnippetMatchResult` (9-value `SnippetMatchOutcome`, closest windows, tiers, filter trail) is rendered by `SnippetErrorFormatter.Build` into a message capped at 6000 chars. Concretely:
- Exceptions are ordinary classes, so each subtype gets typed, wire-safe payload properties: ambiguous -> `Candidates`; snippet not matched -> the `SnippetMatchResult` (or a DTO projection of it: outcome, tier, closest windows with line numbers, filter trail); `DiffApplyException` -> failed hunks; target-ineligible -> reason and suggested tool; unresolved call sites -> the skipped call sites.
- The human message stays (logs, debuggers, fallback), but the tool layer reads the payload, not the message, so nothing is re-parsed.
- Payload types follow `dto-conventions` (reuse existing types such as `AmbiguousCandidate`; no exception object is ever serialized; no stack traces or internal paths leave the server).
- Precedent for "throw before commit, result for rich post-build data" already exists: `MoveMemberAsync` throws NotFound/InvalidArgument/TargetIneligible/NotImplemented before building changes, and `MoveMemberResult` carries `SkippedCallSites` / `PendingLedgerEntries` for the post-build case.
- Tool-layer translation: one translator builds `ResultError` from the exception (code, message, `StructuredDetail` from the payload, large payloads via the existing `ResultError.ForPossiblyLargeDetailAsync` offload). Guidance and hints are composed there, so weak models still get actionable text.

### 3. One translator at the tool boundary
- `ToolErrorMapper.ToResultError` (`ToolException.cs` ~176-225) currently builds `new ResultError(code, message, ex.Message)` (Detail just repeats the message) and structures only ambiguous candidates; its `SolutionNotLoadedException` branch is unreachable behind `ex is ToolException`, and its `workspaceManager` parameter is unused.
- The central filter (`ServiceRegistrationExtensionsBasic.cs:432`) turns an escaped exception into plain text `"Tool call failed unexpectedly ({Type}): {message}"`, losing code and candidates. It should build a structured `ResultError` through the same translator, which also removes the need for the 143 per-tool `catch (Exception) -> ToolErrorMapper` sites over time.

### 4. Target shape of the edit result
- `EditOutcome` shrinks to legitimate non-error values (`Modified`, `AlreadyInTargetState`; `NoChange` and `NoCandidatesFound` are removed per open question 1). Failure values (`TargetNotFound` 166 refs, `DocumentNotFound` 123, `SourceInvalid` 35, `CannotEdit` 172, `CannotMove`/`CannotRemove`/`CannotConvert` 34 combined, `CannotOptimize` 7, `FeatureDisabled`, `Error` 7, `Unset`) are removed last, after callers migrate.
- `UpdatedText` becomes non-nullable on the success shape; `Message` stays for notes and warnings; `ErrorCode` and `Candidates` leave the result (they live on the exception).

### 6. Interfaces: `IOperationResult` (replaces `IResultStatus`) and `IOperationError`

Survey (2026-10-20, `RoslynSentinel.Common/IResultStatus.cs`): `IResultStatus` has 4 members (`IsError`, `Status`, `Code`, `Message`) and 73 implementers (Common 26, Engines 25, Tools.Basic 22; 235 references in 44 files; ~109 tests in `ResultStatusTests`, `AdvancedResultStatusTests`, `ToolsBasicResultStatusTests`). **No non-test code takes an `IResultStatus` parameter, constrains a generic on it, or casts to it**; every status read goes through a concrete type or the serialized `isError` (`HaltStamp.cs:24` says it never touches `IsError`; the orientation breaker resets on the protocol flag at `ServiceRegistrationExtensionsBasic.cs:874`). So today the interface is a labelling convention and changing it has no consumer-side blast radius. That low adoption reflects a pilot that was never completed, not a judgement that the interface is unneeded: about 30 of the 73 implementers are wrappers, envelopes and mappers (`SentinelCallToolResult<T>`, `MigrationEnvelope<T>`, `AppliedChangeSummary`, `Git*Result`, `Doc*Result`), and the purpose is to track one status from origin to destination through every wrap and map without re-deriving it (decided 2026-10-21). `Code` and `Message` are documented error-only but inconsistently so (`AppliedChangeSummary.Message => Note` is success text, `AppliedChangeSummary.cs:96`; `EngineResultBase.Message` defaults to `""`, `EngineResultBase.cs:20`).

**Decided direction (2026-10-21; revises an earlier `IOperationSuccess` draft of this section):**
- **`IOperationResult`** is the one shared status carrier for every result at every layer: engine results, aggregates, wrappers, mappers and the wire envelope. It is the approved rename of `IResultStatus` (finding of 2026-10-16, `proposal_dto_ownership_role_lineage.md:230-233`; no `IOperationResult` symbol exists in source yet). Members: `Status` (the full `ResultStatus` vocabulary, including the new `PartialFailure`), `IsError` as a **derived default member** (`Status.IsErrorStatus()`, never stored independently, so it cannot disagree with `Status`; it maps directly to the wire `isError`), and `Warnings` / `Findings` as default members (proposed in `findings/finding_engine_result_shapes_primitives_and_wrapper_usage.md`). `Code` and `Message` leave the interface: they are error-only, inconsistently used, and the error detail now lives on the exception and on `ResultError`. A single-target engine result always reports `Success` or `AlreadyInState`, so its `IsError` is a constant `false`; that is accepted, because one shape for every result is the point. Aggregates compute `Status` from their parts; wrappers and mappers copy the source `Status`. Add a short convention note to `dto-conventions`: after an engine call, failure means an exception was thrown, so do not branch on `IsError` of a single-target result.
- **`PartialFailure`** is a new `ResultStatus` member (`RoslynSentinel.Common/IResultStatus.cs`), an error status (the existing `IsErrorStatus` already counts everything except `Success` and `AlreadyInState`), so wire `isError` and breaker behaviour are unchanged. Only aggregates set it, through `ResultStatusExtensions.FromFailureCount`: change the signature in place to `FromFailureCount(int failed, int succeeded)` (zero failed is `Success`, all failed is `Failed`, a mix is `PartialFailure`); no `[Obsolete]` shim, because there are 7 non-test callers in 4 files (`BatchTypes.cs` x3, `AsyncBatchEngine.cs` x3, `TestCategoryApplyEngine.cs` x1) plus tests, and the old one-argument form would silently report a mixed batch as `Failed`. Use a call-site-updating tool (`MethodSignature`), one sweep slice. `FromErrorCode` and `FromFlag` never produce it (an exception means the whole operation failed). Before building, check three risks: tool output or model-eval assertions that expect `Failed` for a mixed batch, code that switches on `ResultStatus` or compares `Status == Failed`, and the ~109 `ResultStatus` tests that pin `Failed` for aggregates. The other `ResultStatus` members stay: they are the cause categories `FromErrorCode` and the exception `Category` use.
- **`IOperationError`** is the small exception-side counterpart: `ErrorCode`, `Message`, a payload hook for structured detail, and a `ResultStatus Category` that each exception subtype sets. The category replaces the `ResultStatusExtensions.FromErrorCode` lookup, which maps only 7 error codes to specific statuses and collapses the other 13 of 22 `ToolErrorCode` constants (SolutionNotLoaded, BuildFailed, TestRunFailed, DiffApplyFailed, SessionHalted, ConfirmationRequired, UnresolvedCallSites, ValidationFailed, EolChangeRefused, CollateralChangeRefused, ...) to `Failed`. `ToolException` and the wire `ResultError` implement it. A non-`ToolException` such as `SubAgentLaunchException` (`Tools.Advanced/SubAgentRunNaming.cs:69`) can implement it without changing base class. BCL and unexpected exceptions cannot, so the translator wraps them in an adapter with the generic `Exception` code.
- **The wire envelope keeps the error side.** `SentinelCallToolResult<TSuccess,TError>` still exposes `Code` and `Message` (on its error payload) and `IsError` (derived from its `Status`) because the wire needs `isError` (`SentinelCallToolResult.cs:161-228`; its `IsError` already fails closed). Breaker and filter logic read only that flag, so they are unaffected.
- **Batch and aggregate types keep failure counts** (`BatchResultSummary`, `OperationSummary`, `ApplyChangesResult.FailedFiles`): partial failure is data, not an exception, and `FromFailureCount` stays (with the `succeeded` argument and the `PartialFailure` status above).
- **Compile-time guarantee ("either rich success or rich error")** needs `TSuccess : IOperationResult` and `TError : IOperationError` constraints on the envelope. Many tools use `SentinelCallToolResult<object>` today (e.g. `RefactoringToolHelpers.cs:97`), so the constraint requires typed success DTOs first; treat it as the end state, not S0. `MoveMemberResult` (`MemberRefactoringEngine.cs:20`) already matches the target shape (no error member; failures throw before commit).

**Interface migration order:** add `IOperationError` and `IOperationResult` beside `IResultStatus` (S0d); mark `IResultStatus` `[Obsolete("Use IOperationResult")]`; move implementers in slices bottom layer first; drop error-side members from a DTO when its engine stops returning failures; remove `IResultStatus` last. CS0618 warnings during the migration are expected.

## Alternatives considered, not pursued

- **Keep results, add stricter helpers** (more `RequireUpdatedText`-style guards). Rejected: the survey shows ~50 consumers already map empty text to success; guards must be remembered at each call site, which is the failure mode.
- **Result type with a discriminated union / `Result<T>` everywhere.** Not rejected on principle, but it is a larger rewrite of 148 methods and every consumer, and still requires each layer to unwrap; exceptions already exist, are idiomatic and are loud by default.
- **Numeric packed error codes** (`proposal_tool_error_code_taxonomy.md`). Already recommended against there; unaffected by this proposal.
- **Throw for everything including per-item batch failures.** Rejected: aborts remaining items; batch engines already model failure as data (`ItemFailure`, `FailedFiles`).

## Open questions

1. **Classification of `NoChange`, `NoCandidatesFound`, `AlreadyInTargetState` (DECIDED 2026-10-21).** An engine operation either makes a change or throws. `NoChange` is eliminated: it conflates not necessary, already done, unable to do, invalid request and no target found, which forces every caller up the chain to guess. A tool call that would produce it is a sign of a stale mental model or a wrong parameter, so it is an error. `NoCandidatesFound` throws `ToolNotFoundException` (**amended during S2, 2026-10-24:** only when the caller named a target that is missing; a whole-file or whole-class scan that legitimately matched nothing, such as "no logging calls in this class" or "no assignments to invert", stays a kept `NoCandidatesFound` return with `UpdatedText` set to the unchanged text, because existing tool tests pin "source unchanged" for those; revisit when S3 decides how tools report a no-op). `AlreadyInTargetState` stays a legitimate result for now because it is unambiguous about whether the operation is really an error. Callers choose to swallow, package or re-throw. Consequences: the 17 `NoChange` producers (`findings/finding_nochange_producer_classification.md`) each become a throw with the real cause, or `AlreadyInTargetState` where that is exactly what happened; `GuardEngineResult`'s `NoOpHandling` and the ~50 consumers that map empty text to success go away; an engine that returns `Modified` on a no-op (appendix) must throw or return `AlreadyInTargetState`. Still to settle per producer during S2: which cause each `NoChange` site really is. (Resolves open decision 1 of plan_error_codes_follow_cause.)
2. **Payload shape (DECIDED 2026-10-21).** Typed, wire-safe properties per exception subtype (section 2), not a common `Details` object. Still open within that: which `SnippetMatchResult` fields cross the wire, and the offload threshold (message is capped at 6000 chars today); settle both in S0.
3. **Exceptions without a typed class today:** FeatureDisabled, BuildFailed, TestRunFailed, ConfirmationRequired, UnresolvedCallSites, ValidationFailed, EolChangeRefused, CollateralChangeRefused, Cancelled, TimedOut. Which become exception types vs stay result-level (several are post-build refusals with rich data, closer to the `MoveMemberResult` precedent)?
4. **`MoveAllTypesToFiles*` and solution-wide scans:** not read. It returns a bare `Dictionary<FilePathWrapper,string>` with no per-item failure channel (hypothesis: failures abort the whole call through the tool catch). Needs its own design.
5. **Cancellation (answered 2026-10-21):** yes. 69 generic catches in 23 engine files (not 74); about 49 await with a token and have no guard, so cancellation becomes a failure result or a silent skip (`AsyncBatchEngine` 18, `AsyncOptimizationEngine` 6, `CompilerErrorLookupHelper` 6, `MsToolAugmentEngine` 5, 14 more across other files); 6 more swallow only via synchronous token-taking calls and 13 have no token in the try body. Only `TestCategoryTaggingEngine.cs:72` rethrows `OperationCanceledException`. `PersistentWorkspaceManager.ApplyProposedChangesAsync` swallows it at `:1785` (pre-image read becomes a null pre-image), `:1851` (delete becomes `failed[path]`) and `:1988` (write loop becomes `failed[path]`); also `:1924` (debug diagnostic) and `:2183`. Not checked: the central filter's handling of cancellation, whether `ToolException` derives from `OperationCanceledException` (assumed not), the `Tools.*` and `Server.*` catches, PersistentWorkspaceManager's LoadSolution/reload catches. Decision: S1a audits and fixes this before S1 changes catch shapes.
6. **Interfaces:** (a) name: `IOperationResult` (DECIDED 2026-10-21; an interim `IOperationSuccess` draft was dropped because wrappers, aggregates and the envelope implement the same interface while carrying a failure); (b) `ErrorCode` (exception) vs `Code` (current interface) naming for `IOperationError` (open); (c) partial success: add `ResultStatus.PartialFailure`, set only by `FromFailureCount(failed, succeeded)` (DECIDED 2026-10-21, see section 6); (d) how typed the success DTOs must become before the envelope generic constraints can be applied.
7. **Catch-site count (answered 2026-10-21):** the 71 in 19 files could not be reproduced with any pattern. Engines hold 55 catches of any `Tool*Exception` in 8 files (47 literal `catch (ToolException`, 8 subtype catches; no filtered or multi-type forms). Of those, **36 in 6 files convert to a `DocumentEditResult`** and size S1: `MemberRefactoringEngine` 28 (22 direct, 5 batch aggregators, 1 cascade wrapper at `:361` that drops the code), `BasicRefactoringEngine` 4, `AdvancedStructuralEngine` 1, `MappingEngine` 1, `SemanticRefactoringEngine` 1, `StructuralRefinementEngine` 1. The other 19 return something else: 3 tuple returns that drop `ErrorCode` (`BasicRefactoringEngine` 1993, Member 660 and 1344), 5 in `MsToolAugmentEngine` (return `MsAugmentResult.Fail`), 9 in `SymbolNavigationEngine`, 2 control-flow catches in Member. The 4 lossy catches named in S1a still exist and all drop `ErrorCode`.
8. **Memory note** that `ToolErrorMapper` masks errors as SolutionNotLoaded was not reproduced in current source (the mapper returns it only for a thrown `SolutionNotLoadedException`); the operation-blob path behind the note was not read.
9. **Raw IO exceptions escaping engines (decided: route into this migration, 2026-10-21).** `CheckPackageInconsistencyAsync` on an in-memory test solution throws a raw `FileNotFoundException`: the in-memory project has no `.csproj` on disk and the engine does not guard it. 10. **Not-found contract is inconsistent across engines (found by Track A, 2026-10-21).** Today a missing document/target is reported six ways, so a tool cannot map it uniformly and tests pin whichever the engine happens to return:

    - `TargetNotFound` (UseExceptionExpressions, ThreadSafety MakeMethodThreadSafe).
    - `Error` with code `NotFound` (ThreadSafety ConvertLockToSemaphoreSlim).
    - Already throws `ToolNotFoundException`: OptimizeToValueTask and the logging-conversion path; plus the three `MsToolAugmentEngine` contracts noted earlier.
    Decision needed: one contract (throw `ToolNotFoundException` naming the file) for all of these in S1; every test carrying `// TODO throw-migration` is the work list. Related: the `SyncInterface` tool collapses the engine's distinct causes (class file / class / interface not found, nothing to sync) into one NotFound naming both class and interface (message fixed in 128be7b9, TODO removed); the typed exception should carry the real cause.
11. **`DocumentEditResult.ToJsonSummary()` omits `UpdatedText`**, so GenerateHttpClient / InterpolateStringSafe output is not visible through the tool result. Decide whether the success summary must carry the text (or an offload id) when the edit is not applied to disk.

## Cost / risk

- **Silent swallowers change behaviour when exceptions propagate:** `SemanticRefactoringEngine.InlineVariableAsync` has 4 bare `catch` blocks returning `root.ToFullString()` (`:91`, `:117`, `:132`, `:152`); swallow-only catches around `GetSemanticModelAsync` (`AsyncOptimizationEngine` x5, `AsyncSafetyEngine` x2, `BasicRefactoringEngine` x2, `SymbolNavigationEngine` x2, `CloneDetectionEngine`, `CompilerErrorLookupHelper` x6); 69 generic catches in 23 engine files (recounted 2026-10-21) and 23 in `PersistentWorkspaceManager` around the write chokepoint. Each needs a decision before S1 on that file; `SymbolNavigationEngine` swallowed `InvalidOperationException` as control flow per the plan (line numbers stale, not re-checked).
- **Weak-model guidance must not regress.** `ReplaceSnippet` closest-window messages are valuable; the translator must render the payload at least as well as the 6000-char message does today. `Member(replace)` passes `result.Message` through unreduced; `SummarizeEngineMessage` truncates; the migration should remove that truncation, not keep it.
- **Zero-match and orientation breaker:** the breaker's reset reads `IsError` (`plans/plan_zero_match_is_not_an_error.md`), so what counts as an error changes breaker behaviour; empty-but-valid answers must stay successes.
- **Test churn:** NUnit exact-type hazard (tests asserting `InvalidOperationException` break when the throw type changes); ~250 test references to `EditOutcome.`; `MemberRefactoringTests` (50 refs), `RefactoringToolHelpersTests` and `ResultStatusTests` are the heavy ones.
- **Wire compatibility:** `Outcome` values and `ErrorCode` strings appear in tool output and model-eval assertions; migrate with `[Obsolete]` shims and remove last.
- **Perf:** exceptions as control flow are fine for single-target operations; not for scan/batch hot paths (hence the batch carve-out).
- **Server restart:** server source changes need `Build(fullBuild)` and a restart of the own instance; subagent edits are sequential only.
