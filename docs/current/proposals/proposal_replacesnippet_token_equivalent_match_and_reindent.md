# ReplaceSnippet: token-equivalent matching and server-side indentation of newContent

**Status:** APPROVED 2026-11-14. The owner approved the direction (token-equivalent acceptance plus an indentation-only pass over newContent, no new parameters); the items under "Open questions" are undecided and nothing is built.

## Motivation

`ReplaceSnippet` makes the caller reproduce the file's indentation exactly, and a small model cannot reliably do that. The environment, not the model, should absorb the difference: the file's own text is the authority on indentation, and the server can compare code by its Roslyn tokens instead of asking the caller to retype whitespace.

### How it behaves today (verified against the source, 2026-11-14)

- `ResolveEditMatch` (`RoslynSentinel.Tools.Basic/WorkspaceFileEditImpl.cs:991-1026`) calls `SnippetResolver.Resolve` at `WhitespaceTolerance.IgnoreLineEndings`, case-sensitive. Only `SnippetMatchOutcome.Matched` yields a match; every other outcome is thrown through `SnippetErrorFormatter.Build`. Callers: single path `WorkspaceFileEditImpl.cs:1316`, batch path `WorkspaceFileEditImpl.cs:1636`.
- `SnippetResolver.Resolve` (`RoslynSentinel.Common/SnippetMatching/SnippetResolver.cs`, the "probe the looser tiers" loop, ~121-137) finds a match at `IgnoreIndentation` or `IgnoreAllWhitespace`, wraps it as a near-match and returns `MatchedLooserThanRequested`. `SnippetErrorFormatter.BuildLooser` (`SnippetErrorFormatter.cs:188`) turns that into the error. `WhitespaceTolerance.cs` states the contract: near-matches "are never edit candidates".
- `newContent` is spliced verbatim: `oldText.ToString().Remove(match.Start, match.Length).Insert(match.Start, newContent)` (`WorkspaceFileEditImpl.cs:1345`). The only normalization is line endings (`EolUtilities.NormalizeEol`, `WorkspaceFileEditImpl.cs:1348`).
- There is no caller-facing tolerance parameter, and `docs/current/TODO.md:47` records an owner decision that `ReplaceSnippet` gets no more optional parameters (weak models already struggle with it). The `oldContent` schema text (`RoslynSentinel.Common/McpToolSchemaPatcher.cs:493`) says "Verbatim text to find and replace using literal substring match", which tells the caller indentation must match.

### Measured effect (2026-11-14 eval runs)

772 runs on hosts 112, 113 and 85 (qwen3.5-4b and 9b): 2,003 `ReplaceSnippet` calls, 94 of them rejected as `MatchedLooserThanRequested`. Difference classes among those 94 (lower bounds; one call can have several):

| Difference | Calls |
| --- | --- |
| Indent width differs | 48 |
| No indent where the file has some | 45 |
| Tabs where the file has spaces | 39 |
| Interior whitespace | 4 |
| Trailing whitespace | 1 |

Recovery: 60 retried with the file text quoted in the error and succeeded first time, 9 failed again, 16 detoured through `ReadFile`. So the error text works most of the time, but each rejection still costs at least one full turn for a task whose intent was already correctly located.

Concrete example: `ModelTestingResults/113/Model_CompletesShippingKindStep(5)/20261114-091222-264/turn-4-01-ReplaceSnippet-result.json` reports "line 1: file has 4 leading spaces, snippet has 1 leading tab (file line 5)". `ReadFile` returns 4-space source, so the tabs were generated by the model, not copied.

Across all saved eval history: 104 `MatchedLooserThanRequested` in 70 runs; the near-match tier was `IgnoreIndentation` for 137 difference entries versus `IgnoreAllWhitespace` for 4. Indentation is the failure; interior whitespace is a rounding error.

A second defect hides behind the same cause: because `newContent` is spliced verbatim, a snippet that does match exactly still writes the model's tabs or wrong widths into the file. Journal `.claude/journal/2026-11-09_a8306ec6.md` (line 5) records the mid-line variant: an `oldContent` starting mid-line keeps the file's indentation before `newContent`, so a `newContent` whose second line the model had indented itself came out double-indented and needed a second fix-up call.

## Proposal

Two coupled changes inside `ReplaceSnippet`, no new parameters, no new tool.

### 1. Token-equivalent acceptance (decided in direction)

When the `IgnoreLineEndings` resolve fails, take the candidate regions the existing looser tiers already find and decide each by Roslyn tokens:

- Lex `oldContent` (`SyntaxFactory.ParseTokens` or equivalent) and compare it with the file's tokens over the candidate region. Accept a candidate when the two token sequences are identical in kind and text, so only inter-token whitespace trivia differs.
- Comments are compared too: they must match apart from surrounding whitespace.
- String literal contents (verbatim, raw, interpolated, multi-line) are token text and therefore must match exactly. This is what makes ignoring indentation safe in C#: the only whitespace the check forgives is whitespace the language treats as separator trivia.
- Exactly one token-equivalent candidate is required. Tie-breaker: if several candidates are token-equivalent but exactly one also matches at the strict tier for indentation (or has the closest indentation), take it; otherwise report `Ambiguous` as today.
- Partial-token edges (the snippet starts or ends mid-token) need a rule. Proposed: require a token boundary at both ends of the candidate region, otherwise reject as today.
- The matched span covers whole lines from the line start when the snippet starts at a line boundary, so ownership of indentation is unambiguous. The existing tiers disagree on this (see Open questions): the `IgnoreIndentation` span excludes the first line's indentation, the `IgnoreAllWhitespace` window stage includes it (`WhitespaceTolerance.cs`, the doc comments on the two members). The implementation must pick one convention.

Consequence: the model never needs exact indentation in `oldContent`.

Two refinements the owner has not yet seen (added while verifying, marked for review):

- **Compare against the file's own tree, not a free-standing lex of the region.** If the candidate region were lexed on its own, lines that sit inside a multi-line string literal in the file could lex as ordinary code and pass as "token-equivalent" to an `oldContent` with different indentation, although that indentation is string content. Taking the file's tokens from the file's syntax tree (the tree is already obtained at `WorkspaceFileEditImpl.cs:1310`) avoids this: a candidate whose span starts or ends inside a string token fails the token-boundary rule.
- **The ladder finds candidates; token equivalence only filters them.** Because candidates come from the existing tiers, the token check cannot accept a difference the ladder cannot locate (for example `Foo( x )` against `Foo(x)`: the collapsing tier keeps one space, so no candidate appears). That is acceptable for the measured failures (indentation) and keeps the matcher's real-span guarantee; it is noted so nobody expects the check to be a standalone matcher.

Why this is a different safety argument from the earlier rejection of a tolerant edit path: the 2026-09-10 splice corruption (memory `project_replacesnippet_silent_splice_corruption_adjacent_lines`) came from using the caller's snippet length instead of the real span; that is already fixed (`match.Length`, `WorkspaceFileEditImpl.cs:1305-1309` comment and the splice at `:1345`) and the tolerant matchers already return real spans. The remaining objection to loosening was that a whitespace-collapsed comparison can equate texts that differ in meaning (whitespace inside a string, trailing space in a verbatim string). Equivalence decided on tokens cannot: any difference the language gives meaning to is in token text and fails the comparison.

### 2. Server-side indentation of newContent, indentation-only (decided in direction)

After splicing, ask Roslyn's formatter for its text changes over the inserted lines only (`Formatter.GetFormattedTextChanges` with the inserted span and the document's options, including `.editorconfig`) and keep only the changes that fall inside each line's leading whitespace.

- Intra-line spacing, brace placement and alignment stay as the model wrote them. A full format would surprise the caller's `returnDiff` and is the same class of problem as the open finding `finding_member_replace_drops_leading_blank_line_and_verify_gap.md` ("Member reformats unrelated content").
- Neighbouring lines are never touched.
- It runs on every successful match, exact ones included, so model-generated tabs become the file's indent style. This subsumes a separate "convert leading tabs" item.
- **Fallback** when the edited region does not parse cleanly (formatter indentation is unreliable on broken trees): shift each `newContent` line by the difference between the snippet's base indent and the matched region's base indent, and convert leading tabs to the file's indent unit.
- **Mid-line start:** when the span starts mid-line, the file's existing indentation stays before `newContent`'s first line (the 2026-11-09 double-indent case above); the indent pass must treat line 1 as already indented so lines 2+ are not indented twice.
- Added while verifying (for review): lines whose start lies inside a string literal token (verbatim, raw, interpolated) are content, not indentation, and the pass must skip them, in the formatter path and in the fallback alike. Otherwise the tab conversion or shift would silently change a string's value.

### 3. Response reporting (decided in direction)

The success result states, as facts only, that the match was token-equivalent and/or that indentation was adjusted, so the caller's picture of the file stays correct. `returnDiff` shows the final text. Wording follows `reference_tool_error_text_facts_options_policy.md`.

### 4. Tool description (decided in direction)

The `oldContent` description (`McpToolSchemaPatcher.cs:493`) says indentation need not match, and `newContent` (`:497`) says it is re-indented to the file. No parameters are added.

### Out of scope

- Suppressing LineEnding differences in the looser-tier message (84 of the 94 messages listed CRLF/LF noise) and rewording `BuildLooser` as facts and options are already dispatched separately. Once this proposal lands, the looser-tier message for indentation-only differences mostly stops being reachable on `ReplaceSnippet`, so the two efforts do not conflict.
- `validateOnApply` behaviour is unchanged.

## Alternatives considered, not pursued

- **Loosen `ReplaceSnippet` to the tolerant matcher** (`plan_replacesnippet_whitespace_tolerant_match.md`, closed, never applied). Lost to the splice-corruption history. The real-span guarantee exists now, but whitespace-collapsed equality still cannot tell string content from separator whitespace, so it fails the safety bar token equivalence meets.
- **Alternative (c) of `proposal_internal_whitespace_tolerance_contract_for_snippet_helpers.md`** ("make ReplaceSnippet tolerant"). Rejected there because loosening the edit path "is a separate decision the evidence does not force". The 2026-11-14 numbers are that evidence (94 rejections, 48+45+39 indentation-class differences), and this proposal is that separate decision, made with a stronger equivalence test than the one rejected.
- **A caller-facing tolerance parameter** (alternative (b) of the same proposal, and the `TODO.md:47` owner note). Weak models cannot judge which value to pass, and more optional parameters on `ReplaceSnippet` are ruled out.
- **Improve the error message only.** Already done and is why 60 of 94 recover in one retry; the cost that remains is a wasted turn per occurrence, and the 9 repeat failures and 16 `ReadFile` detours show the message alone does not close the gap.
- **Full `Formatter` pass over the edited region.** Rewrites intra-line spacing and braces the caller chose, so `returnDiff` no longer reflects the edit; same objection as the open "Member reformats unrelated content" finding.
- **Match-time indentation fix only (item 1 without item 2).** Fixes `MatchedLooserThanRequested` but leaves model tabs and wrong widths written into the file by exact matches and by the newly accepted ones.
- **Re-indent only by delta-shift (the fallback as the primary).** Needs no parse but cannot repair a `newContent` whose lines are inconsistently indented, and cannot follow the file's `.editorconfig`; kept as the fallback only.

## Open questions

- **Span convention (item 1):** which of the two existing conventions (exclude first-line indentation as `IgnoreIndentation` does, or start at the line start as the `IgnoreAllWhitespace` window stage does) should the token-equivalent span follow? Whole-line-from-line-start is proposed when the snippet starts at a line boundary; undecided.
- **Preprocessor directives and `#region` lines:** are they tokens or trivia for this comparison, and does re-indenting them match what the formatter would do? Not investigated.
- **Block comments:** whether the formatter re-indents continuation lines of a multi-line comment, and whether the indent pass should leave them alone. Not investigated.
- **Other snippet-anchored tools** (`Member` `contextSnippet` lookups and similar): adopt token equivalence later? Out of scope here.
- **`ApplyDiff` interaction:** it anchors separately; no decision whether it should share any of this.
- **Hypothesis, unmeasured:** that the formatter's indentation for code inside lambdas, collection initializers and switch expressions can differ from the author's style (see Risk). No sample has been taken.

## Cost / risk

- **Touches:** `ResolveEditMatch` and its two callers (`WorkspaceFileEditImpl.cs:1316`, `:1636`); a new token-equivalence helper (proposed in `Common` or an `Engines.*` project so it stays free of MCP types, per the layering rule); the splice region at `WorkspaceFileEditImpl.cs:1345-1348` for the indent pass; the success DTO text; the schema descriptions at `McpToolSchemaPatcher.cs:493` and `:497`.
- **Contract change:** `WhitespaceTolerance`'s documented rule that near-matches "are never edit candidates" gains a narrow exception, decided on tokens, in one call site. The ladder itself and the other callers of `SnippetResolver` do not change; the exception should be stated in the `WhitespaceTolerance` doc comment so the contract stays true.
- **Risk, formatter style mismatch:** the formatter's indentation for lambda bodies, object and collection initializers and switch expressions may differ from the file author's style, so an exact-match edit that used to land verbatim can now be re-indented. Mitigation: indentation-only filter, the success-result note (item 3), `returnDiff`. Residual risk is real until the eval shows otherwise.
- **Risk, always-on indent pass:** it runs on exact matches too, so any bug there affects every `ReplaceSnippet` call, not just the 4.7% (94 of 2,003) that were rejected. Needs the widest test coverage.
- **Risk, string and comment content:** covered by the token-comparison rule and the skip-string-lines rule above; both need explicit tests.
- **Performance:** lex only candidate regions, never the whole file for the token comparison (the syntax tree is already built for the member-name resolver). The formatter call is limited to the inserted span.
- **Makes harder:** the success result now has a second kind of note beside `selectorNote`; the resolve path has a tier-ladder step plus a token step that future changes must keep consistent.

### Verification plan (what "done" means)

Passing the existing tests proves nothing about this change: they cover exact matching and the looser-tier error, not an accepted looser match or the indent pass. Planner responsibility: the plan must list the cases below as required tests; reviewer responsibility: confirm each one exercises the changed path (`ResolveEditMatch` token step, or the indent pass), not only the shared `SnippetResolver` ladder.

Unit tests:

- tabs in `oldContent` against a spaces file, accepted;
- dropped indentation, accepted;
- wrong indent width, accepted;
- a difference inside a multi-line verbatim or raw string literal, rejected;
- two token-equivalent candidates, `Ambiguous` (and the strict-indentation tie-break case);
- mid-line start, lines 2+ not double-indented;
- a `newContent` with lines inside a multi-line string is not re-indented;
- a candidate inside a string literal in the file is not accepted;
- the indent pass on an exact match with tab-indented `newContent`;
- fallback path on a region that does not parse.

Eval: re-run the ShippingKind step-5 prompt variants V7-V11 (script aliases from commit `fa7be962`) and the ten-chain eval on host 113 through `roslynsentinel-evalqueue.ps1`. Target: `MatchedLooserThanRequested` near zero, and no new `ValidationFailed` attributable to re-indentation. The baseline is the 2026-11-14 numbers above.
