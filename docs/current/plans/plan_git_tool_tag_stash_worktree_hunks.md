## Problem

Every git operation the `Git` tool lacks is a permanent, sanctioned hole in the dog-fooding chokepoint (`docs/current/TODO.md` L188-225), and the hook tells agents to use the shell for exactly these. Traced to source on 2026-10-09 (all line numbers below re-measured that day; none of the source anchors had drifted from the previous draft):

1. **`GitOperation` has 16 members and none is tag, stash or worktree** (`RoslynSentinel.Common/ToolEnums.cs:8`, `GitResetMode` at `:327`: status, log, diff, show, stage, add, unstage, commit, revert, reset, branch, checkout, push, fetch, pull, abort). `GitTools.Git` (`RoslynSentinel.Tools.Basic/GitTools.cs:24-178`) has no `action` parameter and ends its dispatch switch with `_ => ... "Unknown operation"`.
2. **The hook says so in words.** `.claude/hooks/enforce-dogfood.ps1` L568-569: "Operations the tool does NOT cover - branch, push, checkout, worktree, rebase, stash, tag - are not blocked; use the shell for those." Mechanically, L546 `$uncovered = 'reset|restore|rm|mv|branch|checkout|switch|push|pull|fetch|clone|worktree|rebase|merge|stash|tag|...'` makes any command line containing one of them un-blockable (L547 `exit 0`), and L540 `$covered = 'status|log|diff|add|commit|revert'`. The message is already stale for branch/push/checkout (implemented); per D-19 this plan fixes only the tag/stash/worktree part and leaves the rest of the uncovered list alone.
3. **Worktrees are the highest in-repo usage.** `RoslynSentinel.Common/GitWorktree/GitWorktreeManager.cs` (PlanStepRunner) shells out to `git worktree add/remove --force` itself (L48-98). CLAUDE.md warns about the resulting `Worktree/` diff trap. The tool needs a worktree surface whose path rules prevent that trap by construction.
4. **Hunk-level staging has no route at all.** `GitImpl.StageAsync` (`GitImpl.cs:1324-1496`) stages whole files (`add -u`, `add -A`, `add -- <paths>`). Journal impressions of the gap (not independently traced, taken from `plan_session_halt_recovery_and_git_gaps.md` Risks 3): `6e6bf59a:L5`, `6406d612:L11`, `a08be84f:L12`, `0017ac93:L12`. The absence of the capability is traced; the journal lines only motivate priority.
5. **`RunGitAsync` cannot carry a patch.** Its `OutputDataReceived` handler appends each line with `stdout.AppendLine(e.Data)` (`GitImpl.cs`, `RunGitAsync` L408-493). Line-event reading drops each line's CR/LF and `AppendLine` re-adds `Environment.NewLine` (CRLF on Windows). A diff round-tripped through it has every line ending rewritten, so a patch rebuilt from that text would not apply to an LF file and would corrupt a CRLF one. Hunk staging therefore needs a byte-exact runner (Step 9). This is the single largest technical risk in the plan.
6. **New code must not copy the exception-leak pattern.** About 16 existing `catch (Exception ex)` blocks put `ex.Message` into `Error` (TODO L227-236, e.g. `GitImpl.cs` StageAsync/CheckoutAsync catch blocks). Every new method here routes unexpected exceptions through one helper that logs and returns a fixed message.
7. **A conflicted `git stash apply|pop` leaves no state the tool can abort.** `DetectInProgressAsync` (`GitImpl.cs:615-636`) checks only rebase, am, cherry-pick, revert and merge state files (`MERGE_HEAD` etc.), none of which a stash apply creates (read 2026-10-09), so `Git(operation: abort)` would report nothing in progress while unmerged paths remain. D-18 specifies the recovery (Step 4).

Linked context: `docs/current/proposals/proposal_journal_digest_followup_decisions.md` (round 3, D-15 .. D-20); `plan_session_halt_recovery_and_git_gaps.md` Risks 3 and 5 (both marked needs-design there; this plan is that design).

## Decision

- **Shape: three new operations plus one shared `action` parameter (D-15).** `GitOperation` gains `tag`, `stash`, `worktree` and `hunks`. The first three take a new nullable enum parameter `action` (`GitAction`: list, create, delete, push, pop, apply, add, remove). `action` is **required** for those three operations (no default, so a destructive action can never be reached by omission); a missing or wrong-for-this-operation value fails with `GitActionRequired` naming the valid values. Precedent: `ProjectDoc` takes `DocAction action` (`DocumentationTools.cs`, `ProjectDoc`). The enum keeps the members `delete` (used by tag) and `push` (used by stash) only; `GitAction` has no member for tag push or stash drop (D-16, D-17).
- **No force, no destructive defaults, with one gated exception.** No `-f`, `--force`, `-D`, `stash clear`, `stash drop`, `--all` (ignored files), `--hard`, and no tag push anywhere. The single exception is `git worktree remove --force`, which runs only when the caller passes the explicit flag `discardUncommittedChanges: true` AND the worktree is verified dirty (D-20). Every other destructive-capable action needs an explicit, structural precondition checked before git runs (clean tree, existing target, explicit index), and the failure says "Nothing was changed."
- **Reuse existing parameters where the meaning is the same:** `ref` (tag target), `message` (tag annotation, stash label), `branchName` / `createBranch` / `startPoint` (worktree add), `files`/`paths` (stash push pathspec, hunk file), `count` (list cap), `repoPath` (list actions and `hunks` only). New parameters: `action`, `tagName`, `stashIndex`, `includeUntracked`, `worktreePath`, `discardUncommittedChanges`, `hunkIds`, `hunkFingerprint`, `lineRange`.
- **Error codes follow the existing pattern** (`GitErrorCodes` + `GitErrorDetails`, `ErrorKind`/`ErrorDetail` on `GitResult`, surfaced as `ResultError.ErrorCode`/`Detail` by the last lines of `GitTools.Git`). Parameter-misuse that is decidable from the arguments alone stays `InvalidArguments` at the tool layer (same as `ref`/`mainline`/`repoPath` today). New codes in Step 1:
  | Code | Used for |
  | --- | --- |
  | `GitActionRequired` | action missing, or not valid for this operation |
  | `GitAlreadyExists` | tag name taken; branch exists on `createBranch`; worktree path not empty; branch checked out in another worktree |
  | `GitTargetNotFound` | tag, stash index, worktree, branch or ref does not exist |
  | `GitInvalidName` | tag name fails `git check-ref-format` |
  | `GitWorkingTreeDirty` | stash apply/pop on a dirty tracked tree; worktree remove with uncommitted changes and no `discardUncommittedChanges` |
  | `GitNoChanges` | stash push or hunk listing/staging with nothing to act on |
  | `GitStashConflict` | stash apply/pop hit conflicts; the attempt was rolled back and the entry kept (D-18) |
  | `GitRefused` | safety-rule refusal (worktree path inside the repo, removing the main/current/locked worktree) |
  | `GitHunkUnsupported` | file kind hunk staging does not handle (untracked, new, deleted, binary, rename, mode-only) |
  | `GitHunkSelection` | `hunkIds`/`lineRange` selects nothing, straddles a hunk, or is malformed |
  | `GitHunkStale` | `hunkFingerprint` no longer matches the file's current diff |
  `GitRefRequired` (existing) is reused for a missing `stashIndex` and a missing `tagName`/`worktreePath`.
- **Disk-changing actions say so.** stash push/pop/apply rewrite tracked files behind the workspace. `GitImpl` has no workspace hook (`GitImpl.cs` only touches `_workspaceManager.GetSolutionRoot()`, L332) and `PersistentWorkspaceManager` has no git-originated-change path (`Search` for `.git` in it: no match), so the next `.cs` write may trip the external-drift halt. Hypothesis, untraced end to end; the same exposure already exists for `checkout`/`pull`/`revert`/`reset`. Mitigation in scope: the stash result carries a `Note` ("Tracked files changed on disk; call LoadSolution(forceReload: true) before editing C#"). Fixing the cause is out of scope.
- **Never leak exceptions:** new methods catch `Exception` (except `OperationCanceledException`), log it, and return `UnexpectedFailure(...)` with a fixed message. A `TimeoutException` from `RunGitAsync` carries a deliberately plain message (`GitImpl.cs` RunGitAsync L~480) and may be relayed.

Risks that are new or still real:

1. *Hypothesis, untraced:* git-originated file changes (stash push/pop/apply, and the existing checkout/pull/revert/reset) trip external-drift detection on the next `.cs` write. Evidence is the absence of any `.git`-aware path in `PersistentWorkspaceManager` and in `GitImpl`; not reproduced. Step 13 can check it live: stash push a `.cs` edit, then attempt a `Member` edit and see whether `SessionHalted` fires. If it does, that is a separate defect needing its own plan (reload or drift-suppression after git operations).
2. **`--unidiff-zero` applies by line number with no context check.** Zero-context hunks cannot detect that the index moved between the diff and the apply (a second process staging the same file in that window). The fingerprint covers the working-tree diff only. Mitigations in the plan: the post-apply `RemainingUnstagedHunks` check and `Warning`. Alternative with more safety and more complexity: `-U1` context and `git apply --recount` without `--unidiff-zero`, at the cost of adjacent edits merging into one hunk.
3. **Line-ending behaviour is the part most likely to surprise.** `core.autocrlf=true` repos produce LF index text with CRLF working files; `git diff` output is LF and so is the patch, which is correct for `--cached`, but this is covered only by the Step 12 CRLF/LF tests, not reasoned to completion. Treat a failure of those tests as a design finding, not a test bug.
4. **`git reset --merge` is an unverified spike.** It was chosen by the owner (D-18) and justified only by the clean-tree precondition; the exact post-conditions (no unmerged paths, clean tracked tree, entry kept) are asserted by the two Step 5 conflict tests, which were not run when this plan was written. A pop whose stash contains untracked files (created with `includeUntracked`) that collide with existing untracked files makes git refuse before touching anything; the plan treats that as a plain `GitError`, also unexecuted. If the tests fail the implementer replies `RESCOPE:`; there is deliberately no fallback design in the plan.
5. **The `discardUncommittedChanges` flag is the one irreversible action in the tool.** Modified and untracked files in the removed worktree cannot be recovered; committed work and the branch survive. The flag name carries the consequence, the description repeats it, a refusal message states it, and the flag is refused on every other operation/action and for main/current/locked worktrees. A clean tree never uses `--force`. A race (the tree becomes dirty between the check and the remove) is theoretically possible and would be removed with the flag set; accepted, because the flag already declared consent to discard.
6. **Worktree remove cannot repair a dirty worktree through this tool without the flag.** Mutating Git operations always target the loaded solution's repo (`GitTools.cs` repoPath guard), so the refusal's "commit or stash inside that worktree first" requires a `LoadSolution` onto that worktree, which is a heavy detour. The flag is now the practical escape for throw-away worktrees (the PlanStepRunner `Worktree/` harness case). Alternatives (accept `repoPath` for `commit`/`stash`) widen the tool; not decided here.
