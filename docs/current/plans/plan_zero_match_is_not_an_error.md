## Problem

Zero-match answers are reported as errors: `Search(mode: text)` returns `IsError: true`, `errorCode: NoMatches` when nothing matches, and `Search` in declaration-kind mode / `ListAll` with a name filter returns the same code. Agents and the journal tooling read that as a failed call (the user-visible symptom in the journal: a correct "nothing is called Foo" answer is counted and phrased as a failure, and I hit it myself on 2026-10-08 when a correct text search of a test file returned `isError: true, errorCode: NoMatches`).

The proposal under review was an `IsBreakerError` property (`[JsonIgnore]`) on the result, so a zero-match could be non-error on the wire yet still feed the orientation breaker. Tracing how the breakers actually decide shows that side channel is NOT needed:

- **Trip side is already independent of `IsError`.** The orientation breaker is fed by an inline match count, not by the result flag: `WorkspaceReadNavigationImpl.SearchSolutionText` calls `_workspaceManager.RecordSearchOutcome(0)` on the zero-match branch (`RoslynSentinel.Tools.Basic/WorkspaceReadNavigationImpl.cs:588`, then throws `NoSearchMatchesException` at 589) and `RecordSearchOutcome(literalResults.Count + regexResults.Count)` on the success branch (line 596). `OrientationCircuitBreaker.RecordSearchOutcome` (`RoslynSentinel.Common/OrientationCircuitBreaker.cs:22-40`) counts consecutive zero-match calls and trips at the threshold (default 10). The filter explicitly does not record (`ServiceRegistrationExtensionsBasic.cs`, `AddOrientationBreakerFilter`, comment "recorded inline ... not here. Recording it a second time here would double-count"). Only `Search(mode: text)` feeds it; the `ListAll` name-filter miss (`WorkspaceReadNavigationImpl.cs:403-410`) never counts toward a trip.
- **Reset side DOES read `IsError`**, in one place: `AddOrientationBreakerFilter` resets the breaker when `!isTextSearch && automaticBreaker.IsTripped() && result.IsError != true` (the `if` after the `await next(...)` call, `ServiceRegistrationExtensionsBasic.cs`, about line 745). While tripped only `ListAll`, `ListSolutionItems`, `GetFileOutline` and `ReadFile` get through. Today a `ListAll` name-filter miss is an error, so it does not reset. If that miss became a success, `ListAll(nameFilter: "Typo")` would silently reset a tripped breaker and the agent would be back to guessing. This is the one real coupling, and it is fixable inside the filter with a field the envelope already serializes (`totalRecords`), not with a new side channel (see Decision).
- **The unrecoverable breaker is unrelated.** `IUnrecoverableBreaker` is tripped only by an operation-blob integrity failure (`UnrecoverableCircuitBreaker.Trip`, `RoslynSentinel.Common/UnrecoverableCircuitBreaker.cs:53`), and its refusals are `IsError: true` (`AddUnrecoverableBreakerFilter`). Nothing about zero matches touches it, and its refusals must stay errors.
- The current behaviour is a documented, deliberate decision: `ToolErrorCode.NoMatches` says it is "surfaced as an error (rather than a quiet success with a warning) so a client relying on the protocol-level IsError flag sees it as a signal to change approach" (`RoslynSentinel.Common/SentinelCallToolResult.cs`), and `OrientationBreakerFilterTests.cs:112` asserts "Zero matches should surface as a protocol-level error so the agent treats it as a signal to change approach". The rationale (steer weak models away from retry loops) is real; the breaker is what actually enforces it after N tries.

Consumers of the flag that may be affected (hypotheses; not traced end to end): the journal `PostToolUseFailure` hook (`.claude/settings.json`) and Stop-nudge failed-call counts, the digest's failed-call ranking, and any prompt text that tells a model to "react to NoMatches". The in-repo assertions are listed in Steps 2-3.

## Decision

1. **Zero matches become a success with an empty payload** for `Search(mode: text)` and for the name-filter miss in `ListAll` / `Search` declaration-kind mode: `IsError: false`, `SuccessData` = the normal empty shape (`TextSearchResult` with empty lists; empty `SolutionSymbolEntry` list), `TotalRecords: 0`, and `StatusMessage` carrying exactly the guidance text that the error message carries today (what was searched, "use mode: symbol", "pass exactMatch: false", "ListAll to browse"). `WarningDetails` is left null.
2. **The breaker keeps its inline recording** (`RecordSearchOutcome(0)`), untouched. When this call is the one that trips it, the result carries the same `OrientationBreaker` finding it carries today, now on a successful result. After the trip, the refusal of non-allow-listed tools stays `IsError: true` (a guardrail, not an answer).
3. **Close the only coupling in the filter**: the reset condition becomes `!isTextSearch && automaticBreaker.IsTripped() && result.IsError != true && !IsEmptyListAllResult(toolName, result)`, where the helper returns true when `toolName == "ListAll"` and the serialized body has top-level `totalRecords` equal to 0. It reads a field already on the wire (the same JSON-parse approach `AddToolErrorFilter` uses), so no `IsBreakerError`, no `Meta`, no context item, no error-code allow-list is needed. Restricting it to `ListAll` avoids touching `ReadFile`/`GetFileOutline`, which may legitimately report zero records.
4. **Error codes that are non-breaker:** only `NoMatches`, and it stops being an error at all. Every other code stays an error and none feeds the orientation breaker: `InvalidArgument` (including the glob-matches-zero-files case, `GlobSyntaxException`, thrown before `RecordSearchOutcome` so it never counts), `NotFound`, `Ambiguous`, `SolutionNotLoaded`, `SessionHalted`. The constant `ToolErrorCode.NoMatches` and its `ResultStatus.NotFound` mapping stay (a test and external clients reference them); only the doc comment changes.

## Risks and open decisions

- *Decision for the human (the real one):* this reverses a documented design choice (error-on-empty as a "change approach" signal). Tradeoff: success-shaped empties stop being counted as failed calls and stop reading as failures (what the journal complaints are about), but a weak model that previously reacted to `isError: true` now relies on `statusMessage` and on the breaker (which still trips at 10 and now refuses with `isError: true`). If you want a softer middle path, keep Step 1 and Step 2 (ListAll and kind mode) and defer Step 3 (text search), since kind-mode misses never fed the breaker. Recommendation: do all steps; the breaker, not the flag, is the enforcement.
- *Decision for the human:* trip threshold. The default is 10 (`OrientationBreakerOptions`); with errors no longer shouting "failed", ten silent empties may be more than needed. Not changed here; `--orientation-breaker-threshold` already exists.
- Hypothesis, not traced: clients or prompts that branch on `errorCode == "NoMatches"` (for example SubAgent or ModelEval harness code). `Search(text, "NoMatches")` on 2026-10-08 found only the files listed above plus a `SubAgentEvalResultTests.cs` string literal (`"ReplaceSnippet|NoMatches|a.cs"`, a repeated-failure signature, unrelated to this code). Prompt/doc files were not searched exhaustively.
- The `IsEmptyListAllResult` helper depends on the serialized envelope property name `totalRecords`; Step 1's test pins it, so a rename of the property fails loudly.
- `IsBreakerError` (the original proposal) would also have worked for the trip side but would still need the reset rule in Step 1, because reset looks at the result, not at the exception; it is strictly more machinery for the same behaviour.
