## Problem

The three costliest propagation sweeps into `RoslynSentinel.Engines.Advanced` since 2026-10-19 were policy changes to logic that every engine writes out for itself: how a failure is carried (typed exceptions replacing failure results), what a not-found message says, and how a name is matched to a declaration (first-match ambiguity). A change with one owner cost Advanced almost nothing (stale-read guard: 0 of 10 commits touched it; ReplaceSnippet matching: 0 of 14).

What a throw site still assembles by hand (all verified against source 2026-11-21):

- **The lookup triple.** Example `AdvancedStructuralEngine.cs:36-58` (`ConvertAbstractClassToInterfaceAsync`): `root.DescendantNodes().OfType<ClassDeclarationSyntax>().Where(c => c.Identifier.Text == className).ToList() ?? new List<...>()`, then `NameTargetLookup.RequireSingle(..., "Class", className)` (returns null on zero), then a hand-built `new ToolNotFoundException($"Class '{className}' not found in {Path.GetFileName(filePath)}. " + DeclarationNotFoundDetail.Build("class", "className", className, names, filePath.ToString()), MissingTargetKinds.Class, className)`. The same cluster is repeated at `:70/:98`, `:188/:191`, `:533/:536`, `:560/:563`, `:2328/:2332` and in other engines. The kind, the name and the tool parameter name are each written two or three times per site, and the message prefix differs by site: `not found in {Path.GetFileName(filePath)}.` (`:58`), `not found in '{filePath}'.` (`:191`), `not found.` (`:2332`), `Method not found.` (`:1327`), `Class or method not found.` (`AsyncOptimizationEngine.cs:337`).
- **A bare message with no orientation.** `ToolNotFoundException("Containing class not found.", ...)` and similar at `AdvancedStructuralEngine.cs:629,723,744,751,830`; `"Cannot edit: target not found. ..."` (a legacy `Cannot edit:` prefix the typed-throws proposal wanted stripped) at `BasicRefactoringEngine.cs:2415,2560`.
- **A null syntax root reported as `ToolInvalidArgumentException` in ~12 wordings.** `"Source invalid."` (12 lines in Engines.Advanced), `"Failed to get syntax root..."`, `"Could not parse '<file>' into a syntax tree, so ..."` (13 lines in Engines.Advanced, 5 across the three phrasings in Engines.Basic). One engine already has a helper, `StructuralRefactoringEngine.RequireSyntaxRoot` (`AdvancedStructuralEngine.cs:1149`, used once, `:1251`); `MemberRefactoringEngine` instead throws `MemberRefactoringNotFound.Unavailable("syntax root", ...)` (a `ToolNotFoundException`, `MemberRefactoringEngine.cs:3327`). Two engines, two exception types, for one cause.
- **Not-found coded as something else, ambiguity hand-rolled.** `InlineClassAsync` throws `ToolTargetIneligibleException` for "No target class found" (`AdvancedStructuralEngine.cs:206,229`); `InlineMethodAsync` counts `candidates.Count > 1` itself and throws `ToolTargetIneligibleException` (`:2102-2108`) instead of `ToolAmbiguousMatchException`, and reports a null semantic model as "Method not found" with an empty detail (`:2096-2099`).

## Decision

Reuse what exists, add one lookup layer, ratchet the rest. No new exception type and no change to `ToolNotFoundException`.

1. **`MemberRefactoringNotFound` (Engines.Basic, 298 lines) becomes the one owner of declaration-miss exceptions and messages.** It already renders the standard (ranked "Did you mean ... Retry with param: 'X'" or the nothing-similar fact plus `GetFileOutline`), the other-kind fact (`OtherKindFact`), `Unavailable` for a document without a syntax root, and keeps `MissingTargetKinds`. Engines.Advanced has zero uses of it today. It cannot move to `Common`: `MemberNames` calls `SyntaxTargetResolver.GetMemberName` (Engines.Basic). It stays; Engines.Advanced and the other Basic engines call it. Missing factories (new): `Interface`, `Property`, `Field`, `Parameter` (method parameter), each a thin call into `Declaration(...)`.
2. **One new static class `DeclarationLookup` in `RoslynSentinel.Engines.Basic`** with `Require*` methods that do the Where, `NameTargetLookup.RequireSingle` (ambiguity, multi-target and partial collapsing, unchanged), and the miss throw in one call, so a site is `var classNode = DeclarationLookup.RequireClass(root, className, filePath.ToString());`. Final signatures are in Step 2. It reuses `DocumentLookup.RequireDocument`, `ProjectLookup.RequireProject` and `MemberRefactoringNotFound`; it adds only what is missing: declaration-by-name and the syntax-root guard. `StructuralRefactoringEngine.RequireSyntaxRoot` is generalized into `DeclarationLookup.RequireSyntaxRoot` (migration-first: the old method stays, `[Obsolete("Use DeclarationLookup.RequireSyntaxRoot")]`, one caller).
3. **The ratchet extends the existing style.** A new `ThrowAndLookupRatchetTests` (Tests.Basic) counts, per file, (a) raw `new ToolNotFoundException(` outside the owner files, (b) `NameTargetLookup.RequireSingle(` calls in Engines.* outside `DeclarationLookup`, (c) null-root throws, with a baseline taken from the Step 1 census that may only shrink, modelled on `FirstMatchRatchetTests` (exact counts, stale and higher both fail). `FirstMatchRatchetTests` is not replaced: it already is the ratchet for name-keyed `First/Single` picks; this plan only works its 30 baseline keys down. Shared scan helpers go into one new class so the new test is not an 11th copy of `RepoRoot()`.
4. **Order:** census, skeleton, helper bodies with tests, ratchet, then migration. Engines.Basic and the Basic engines behind kept tools first. Engines.Advanced slices are last and gated on D1.

Text and code effect of every migration slice: wording changes (the prefix becomes "X 'n' was not found in 'path'." with the standard tail), codes and missing-target kinds do not (except null-root under D2). So every migration slice is **text-changing** and ships with its assertion updates.

## Execution rules

- Every step ends compile-green: `Build` 0 errors, and `scripts/build.ps1 -Flavor Solution` for any change in `Common` or `Engines.*` (Advanced is additive). One `Build` or `RunTest` at a time. Implementers never run tests; the dispatcher runs the named classes and compares with `docs/known-failing-tests.{Basic,Advanced,Solution}.txt` and `docs/known-build-warnings.*.txt`, reporting only new failures.
- Tiers (`.claude/implementer-tiers.json`, 2026-11-21): depth `tier` 1 = D1 (3 files, 15 edits, 1 acceptance, 35 tool calls); sweep `tier` 0 = S0 (1 operation, 8 files, 25 call sites, 2 projects, 30 tool calls). A slice that names an engine file and its test files must fit 3 files; a count over 15 edits splits.
- Per-site edits use `ReplaceSnippet` batchEdits, one call per file with `withinMember` selectors, definitions-first (see `reference_edit_tool_gotchas.md`); copy the old text from `GetMethodSource`. Whole-method rewrites use `Member(operation: replace)`.
- **Finding the assertions a slice breaks:** before the slice, `Search(mode: text, includeTests: true, query: "<the old prefix, e.g. not found in|was not found|Source invalid|Could not parse|Failed to get syntax root>", fileGlob: "<the engine's test projects>/**/*.cs")`. Today 151 lines in `RoslynSentinel.Tests*` match `(Contain|StartWith|EqualTo|Match)\("...(not found|was not found|Source invalid|Failed to get syntax root|Could not parse)`, 50 of them in the three Advanced test projects (`Tests.Advanced`, `Tests.Tools.Advanced`, `Tests.Battery.Advanced`; first hit `BugFixTests.cs:167`). The slice brief lists the test files from that search; after the edit the dispatcher runs those classes through `RunTest` and the failing ones are the work list. An updated assertion must still check the fact or option that remains (candidate present, prefilled call, nothing-similar fact), never be deleted or loosened.
- String-coupled consumers: a consumer that parses a message breaks silently when the text changes (earlier found: `ScanTools.cs:1096`, fixed; `AsyncifyTools` `ClassifyUpliftSkipReason` still matches reason text, per the typed-exceptions proposal). Step 1 re-searches `Message.Contains(` / `.Message.StartsWith(` in Tools.* and Engines.* and lists each coupling; a slice that touches a coupled message moves the consumer to `ErrorCode`/exception type first.
- Messages carry facts and options only (no "must", "stop", "if your task is"); the helpers are the only place wording lives.
- Inline `// TODO` for anything noticed and deferred, plus one INBOX line.
