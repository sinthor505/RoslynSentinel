Design choices (all follow the existing patterns, no new mechanisms):
- **Read block:** a new `Read` branch in `enforce-dogfood.ps1` with the same shape as the Edit/Write branch (`.cs` suffix, `Worktree/` exempt, `Test-PathOutsideRepo` exempt, `Exit-IfBypassed '' $filePath`, then `DenyBypassable`). Bypass routes are unchanged: out-of-repo auto-exempt and the `.claude/bypass.local.json` token with `"tools": ["Read"]`. The deny text names `ReadFile`, `GetFileOutline`, `GetMethodSource`, `Search`, `FindReferences` and the blocking-finding rule. `Read` is added to the settings.json matcher. A guard test fails if an agent that has `Read` but no `*` and no MCP ReadFile tool is not on an explicit no-C# allow-list, so a future agent cannot be stranded.
- **Launcher:** `scripts/Launch-RoslynSentinelHttpServer.ps1`, parameters `-Mode` (default `all`), `-Tools` (maps to `--include-tools=`), `-Port` (default 5100, the server default), `-Solution` (optional, maps to `--solution=`), `-Configuration` (Debug), `-DryRun`. It builds `RoslynSentinel.Server.Advanced\RoslynSentinel.Server.Advanced.csproj` with `dotnet build -c Debug -o <dir> --nologo -v quiet` (the recipe at `scripts/roslynsentinel-mcp-launch.ps1:298`) into `bin-vscode\http-<port>-<yyyyMMddHHmmss>`. That name deliberately does NOT match the stdio instance pattern `^[0-9a-f]{8}-[0-9a-f]{8}$` (control script line 79), so the stdio sweep and `Get-StdioInstanceFolders` never touch or list it. `bin-vscode/` is gitignored.
- **Control script (D-11):** a new `Build-HttpCopy` function in `roslynsentinel-vscode-control.ps1` runs the same `dotnet build ... -o $httpOutDir` recipe; `Restart-HttpCopy` (line 287) becomes stop -> `Build-HttpCopy` -> start, and does not start when the build fails (the copy stays stopped and the message says so). `start`, `status`, `stopall*` are unchanged. The `build` verb keeps delegating to `build.ps1` for the solution build and then calls `Restart-HttpCopy` (which now builds the HTTP copy), so its documented meaning ("rebuild, then restart") is true again.
- **Sweep (D-12):** `LargeResultHelper.SweepExpired(solutionRoot, maxAge, utcNow?)`: non-recursive, only `largeresult_*.json` directly in that folder, by `LastWriteTimeUtc`, per-file `IOException`/`UnauthorizedAccessException` swallowed (a concurrent session may hold a file), returns the deleted count, never throws. Called from `PersistentWorkspaceManager.LoadSolutionAsync` after a successful load, via a private fire-and-forget method that wraps it in its own try/catch, so it never blocks or fails a load and does not run while `_solutionLock` is waited on. Because it hooks the load itself, it covers every server (stdio, HTTP, Basic, Advanced), every start, and every manual `LoadSolution`; no `Server.*` file is touched.

## Why the ReadFile lineEndings / hasBom work was dropped (D-13/14)

The earlier draft added `lineEndings` and `hasBom` to the `ReadFile` response (steps 14-15, a new `FileFormatProbe` helper). The owner dropped it: models should not deal with BOM or line endings at all. `WriteFile`, `ReplaceSnippet`, `ReplaceSnippetBatch` and `ApplyDiff` already normalise model-supplied text to the file's dominant EOL (`EolUtilities.NormalizeEol`), and `EolChangeGuard` is only a tripwire for tool bugs, not something a caller should steer around. The one gap found (`ChangeSignatureAsync` had no normalisation) was fixed in a separate slice (commit `276afac`). Showing format fields would invite models to reason about something the tools already handle, and would add a nullable `hasBom` to every `ReadFile` response shape. If an enum is ever needed for this, avoid nullable fields. Nothing in this plan references `FileFormatProbe`.
