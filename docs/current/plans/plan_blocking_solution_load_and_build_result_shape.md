### What an agent needs from Build (answers the proposal's open question)

| Errors | Situation | What the response must contain |
| --- | --- | --- |
| 0 | green | outcome, projects built, warning count, duration. No stdout, no warning list, no errors list. |
| 1 | one project, one file | that error in full: id, project, `file:line:col`, message. |
| 10 | a few files | all 10 details, grouped by project (about 3 KB). |
| 100 | several files, maybe two projects | counts by project and by file (top 10) and by code (top 10); the first `maxDetails` (default 20) details, root-cause project first; `OmittedErrorCount`; a `FullDiagnosticsResultId` for the rest. |
| 1000 | usually one broken upstream project | same as 100, plus an explicit `SuppressedDownstreamErrorCount` and the root-cause project names, so the agent fixes the upstream project and rebuilds instead of paging. |

Stdout is not needed when the build parsed correctly. It is the only evidence when a failed build parsed zero errors, so it is returned in that case and when `includeOutput: true`.

## Decision

### Part A (owner design D-4, D-5, D-6)

1. **Status enum.** New `SolutionLoadStatus { NotLoaded, Loading, Loaded, Failed }` (Common, string-enum JSON like the other enums in `ToolEnums.cs`). `ISolutionProvider` gains a lock-safe read-only property `SolutionLoadStatus SolutionLoadStatus { get; }`. In `PersistentWorkspaceManager` it is computed without taking `_solutionLock`: `Loading` while the pending-load count is above zero, otherwise the last terminal status. Counter, terminal status and a completion signal are mutated only under a tiny private `lock (_loadStatusSync)` (never `_solutionLock`), so a reader can never observe "count 0, terminal stale".
2. **The count rises before the lock wait.** `LoadSolutionAsync` registers itself (status `Loading`) right after resolving the path and before `await _solutionLock.WaitAsync`, so a request arriving while the auto-load is queued behind anything still sees `Loading`. Terminal status is set before the count falls; the signal completes after the load has released `_solutionLock`.
3. **The wait lives inside `GetCurrentSolutionAsync`** (D-4): while `SolutionLoadStatus == Loading` it awaits the load signal for at most `SolutionLoadWait.DefaultTimeout` (30 s), then takes the lock as today. If still `Loading` after the limit it throws the new `SolutionLoadTimeoutException` (a `ToolException`, code `SolutionLoadTimeout`) with a message that names the wait and the retry. There is no request filter and no exempt-tool list (the earlier filter design is removed): a tool that never reads the solution never waits.
4. **Lock-free paths** (how they wait): `ISolutionProvider.WaitForLoadAsync(TimeSpan timeout, CancellationToken)` returns the status after waiting (`Loading` means the wait timed out). The one central lock-free choke, `PersistentWorkspaceManager.ResolveFromWire`, calls it synchronously (bounded by 30 s, a pool thread blocks; there is no `SynchronizationContext` on the server) when `CurrentSolution is null` and status is `Loading`, then re-checks. After a timeout it returns the same `NoSolutionLoaded` wrapper as today, so `ReadFile` of an absolute path still falls back to reading from disk. State-only readers (`GetLargeResult`, `GetWorkspaceHealth`) do not wait.
5. **Timeout = cancel (D-5).** `IWorkspaceMutator` gains `LoadSolutionAsync(string solutionPath, string? baseRepoDir, TimeSpan timeout, CancellationToken cancellationToken = default)`. The two existing overloads delegate to it with `SolutionLoadWait.DefaultTimeout`. The timeout is a linked `CancelAfter` token that covers BOTH the wait for `_solutionLock` and `OpenSolutionAsync`, so a stuck load cannot deadlock callers. When it fires (and the caller's own token did not) the load is cancelled and `SolutionLoadTimeoutException` is thrown. The swallow-all catch rethrows when the load token is cancelled. A caller that merely *waits* on someone else's load never cancels it; the load cancels itself on its own clock.
6. **Blast radius of threading the timeout (measured).** A required timeout parameter on `LoadSolutionAsync` would change 103 callers of the 2-argument overload and 5 of the 3-argument one (almost all tests); rejected. A new overload has zero call-site edits. `GetCurrentSolutionAsync` (7 references in 4 files by `FindReferences`, plus the `IWorkspaceReader` delegate) keeps its signature. Only the `LoadSolution` tool exposes `timeoutSeconds` (default 30). Internal callers, including the start-up auto-load, stay on the 30 s default (D-5).
7. **Manual `LoadSolution`** waits for a running load first (using its own `timeoutSeconds`), re-checks "already loaded" (this removes the double load), and otherwise loads with `LoadSolutionAsync(path, baseRepoDir, timeout, ct)`. It passes the caller's token, so a client cancel now really cancels.
8. **Failure memory.** `SolutionLoadState` gets a trailing `string? LastLoadFailure`; `SolutionNotLoadedMessage.Build` appends it when no solution has loaded since start, so a start-up load that timed out or failed is no longer only visible in the server log.
9. `McpServerStatus` exposes `solutionLoadStatus` (the enum).
10. **Launcher auto-load heuristic** (`scripts/roslynsentinel-mcp-launch.ps1:315-333`): kept as is (D-6). No launcher change.

### Part B (owner decisions D-7, D-8, D-9)

1. Keep `BuildResult` as the tool's `SuccessData` type and its JSON names (D-8: extend additively, no new response type). `SubAgentEvalResult.Build` (`Common/SubAgentEvalResult.cs:69-73`) and `PlanStepRunner/Program.cs:273` read `outcome`/`errorCount`; six tests in `Tests.Tools.Basic/BatteryTwentyTests.cs` (lines about 987, 1000, 1020, 1071, 1084, 1107) cast `SuccessData` to `BuildResult`.
2. Add trailing optional members to `BuildResult`: `Breakdown` (counts by project and file, with a root-cause flag per project), `OmittedErrorCount`, `SuppressedDownstreamErrorCount`, `FullDiagnosticsResultId`, and a `[JsonIgnore]` `FullDiagnostics` carrier so the engine can hand the uncapped lists to the tool boundary without changing what other callers (`GetDiagnostics`, `GetWorkspaceHealth`) serialise.
3. The engines produce the full picture (project on every diagnostic, uncapped lists); a pure projector in `Common` shrinks it for the wire at the tool boundary:
   - green: `Outcome`, `ProjectsCompiled`, `WarningCount`, `Duration`; no lists, no tails, no summaries.
   - failed: `Breakdown`, `ErrorSummary` (top 10), the first `maxDetails` errors (root-cause projects first), `OmittedErrorCount`, `SuppressedDownstreamErrorCount`; tails only when nothing parsed or `includeOutput: true`; warnings only when `includeWarnings: true`.
   - messages are cut to 300 characters so the typed payload stays under the 15 KB offload threshold (20 details at about 300 B each is about 6 KB).
4. `Build`'s `maxDetails` default becomes **20** (D-7) in its three declarations. `GetDiagnostics` and `RunTest` keep 50.
5. **Dependency order** is by classification, not by re-running (D-9). A project with errors is a root cause when none of the projects it transitively depends on has errors; otherwise its errors are downstream. The map comes from Roslyn's `ProjectDependencyGraph` (`GetProjectsThatThisProjectTransitivelyDependsOn`). Step B1 checks whether `dotnet build` already stops at the root layer.
6. **Offload rule:** the full lists are stored with `LargeResultHelper.StoreRawJsonAsync(json, solutionRoot, ct)` (`Common/LargeResultHelper.cs:80`; precedent `ValidateAndApplyHelper.StoreChangedContentAsync`, `Common/ValidateAndApplyHelper.cs:176`) only when the build failed or the lists were truncated; the id goes in `FullDiagnosticsResultId`. A green build stores nothing.
7. `StatusMessage` stays the one-line headline (`SummarizeBuild`, `WorkspaceBuildTestImpl.cs:169`); the generic offload filter already relays it, so even a response that is somehow too large keeps its verdict inline.

## Risks and open decisions

Decided (owner, round 3, 2026-10-09):

- **D-4** Wait inside `GetCurrentSolutionAsync` driven by `SolutionLoadStatus {NotLoaded, Loading, Loaded, Failed}` and a lock-safe property; 30 s limit covers both waiting on a running load and a load the call starts itself (Steps A2a, A2b).
- **D-5** Timeout cancels the load and returns a clear error; `timeoutSeconds` (default 30) on `LoadSolution` only; internal callers keep the default, no wiring (blast radius of a required parameter measured at 103 + 5 callers; a new overload was used instead).
- **D-6** Launcher auto-load kept as is.
- **D-7** `Build` `maxDetails` default is 20.
- **D-8** `BuildResult` is extended additively; no new response type.
- **D-9** Project-by-project re-run not planned; root-cause classification from the project graph is used.

Risks that are new or still real:

1. **A start-up load longer than 30 s is now cancelled** (D-5 with internal callers on the default). The start-up auto-load goes through the same limit, fails, logs the error and leaves status `Failed`; every later call then says "No solution is loaded ... The last load attempt failed: ..." until someone calls `LoadSolution` with a larger `timeoutSeconds`. Real load times are not measured; Step A2b logs the elapsed time and the final live check reads it. If this repo's load approaches 30 s, the cheapest remedy is a start-up option or a longer default, which is an owner call and not part of this plan.
2. **Test-suite exposure.** The 30 s limit also applies to the 103 test callers of the 2-argument overload. Fixture solutions load in seconds (hypothesis, not measured under full parallel load). If solution-scope `RunTest` shows new load timeouts, move the affected fixtures to the 4-argument overload with a larger timeout rather than changing the production default.
3. **Does `MSBuildWorkspace.OpenSolutionAsync` honour cancellation promptly?** Unverified. If a phase ignores the token, the timeout fires only when the next check runs, so the 30 s bound can overrun. The 1 ms test in Step A3 proves the pre-cancelled case only; the live check (d) exercises a real reload.
4. **A cancelled reload keeps the earlier snapshot.** `CurrentSolution` is only replaced after `OpenSolutionAsync` returns, so a timed-out `forceReload` leaves the previous solution readable and status `Loaded`, but the old `MSBuildWorkspace` was already disposed (`_workspace?.Dispose()` at the start of the load) and a new empty one is current. Reads of `CurrentSolution` are unaffected; `GetDiagnostics` (`_workspace.Diagnostics`) reports the empty workspace's list. Deliberate, flagged for review.
5. **`ResolveFromWire` blocks a pool thread for up to 30 s** while a load runs. Only calls that arrive mid-load pay it, one thread each; the server has no synchronization context so there is no deadlock hazard. It is the single sanctioned sync-over-async wait (commented in code).
6. **A waiter never cancels someone else's load.** A tool call that waits behind a manual `LoadSolution(timeoutSeconds: 120)` gives up after 30 s with the wait-timeout message while that load keeps its own 120 s clock.
7. **Client cancellation now cancels a load.** The swallow-all catch used to turn it into a partial solution; it now propagates. Intended, but it is a behaviour change for a cancelled `LoadSolution` request.
8. **Double-load race window.** Between the tool's "is a load running?" check and its own `LoadSolutionAsync` start, a second loader can still begin. The window is microseconds and the lock serialises the two loads; accepted.
9. `LoadSolutionAsync` now registers as `Loading` before taking the lock, so `LoadState.LoadInProgress` is true while a load is merely queued behind a writer. The `Build` message text for that case stays valid.
10. **Part B hypotheses (unchanged):** the green-payload savings are measured (94 files); the projector's runtime cost is negligible but unmeasured; whether quickBuild's `int.MaxValue` request (Step B5) is memory-significant on a 1000-error solution is a hypothesis (the diagnostics already exist in memory in `allDiagnostics`); the NuGet project-level error format in `DiagnosticLineRegex` is pinned by canned lines, not by a real run.
11. Journal entries are impressions: the two `cc715aa0`/`93fd2d31` Build notes were traced to source (every fullBuild payload exceeds 15 KB; measured), not taken on trust.
