`PersistentWorkspaceManager.OnDebounceTimerElapsed` (fires from the FileSystemWatcher debounce timer) had a bug in its full-solution-reload branch: it called `_workspace.OpenSolutionAsync(slnPath)` and reassigned `CurrentSolution` in one step, reusing the existing long-lived `_workspace` instance. If `OpenSolutionAsync` threw partway through — observed cause: the `.slnx` transiently missing because a `git checkout`/reset was running concurrently against the loaded solution's directory — the reused `_workspace`'s internal MSBuild project state was left half-reloaded. Every subsequent tool call then saw mass `CS0234`/`CS0246` errors (`Microsoft.CodeAnalysis`, `ModelContextProtocol` "not found") across nearly all files, even though `GetWorkspaceHealth` still reported `loadErrors: []` and a plausible project/document count — the workspace looked loaded but every reference was broken. Only a fresh explicit `LoadSolution` call (which always creates a brand-new `MSBuildWorkspace` via `LoadSolutionAsync`) recovered it.

This was discovered via a failed agent BulkComment test against a separate clone (`RoslynSentinel-AgentCommentingTest`): `BulkComment` reported `commentedThisCall: 0` with all ~4479 seeded members skipped as "apply validation failed (26 diagnostic(s))" — a real downstream symptom, not a BulkComment bug. The server log's `http-host20260826.log` showed the actual root cause: `Processing 334 file system changes...` → `Reloading entire solution...` → `FileNotFoundException: Solution file not found` from `MSBuildWorkspace.OpenSolutionAsync` at `PersistentWorkspaceManager.cs:537`, caught only by the outer generic `catch (Exception ex)` that logs and moves on without any recovery.

**Fix** (commit `c3c9463`): the reload branch now builds a brand-new `MSBuildWorkspace` (same `NuGetAudit`/`NuGetAuditLevel` properties as `LoadSolutionAsync` and the existing `ReloadWorkspaceFromDiskAsync` background-reload path) and only swaps it into `_workspace`/`CurrentSolution` after `OpenSolutionAsync` succeeds; on failure the new workspace is disposed and the exception is rethrown, leaving the old (still-valid) `_workspace`/`CurrentSolution` untouched. Note `ReloadWorkspaceFromDiskAsync` itself (used from `ApplyProposedChangesAsync`'s post-write background reload) already had this correct pattern and was not the buggy path — it acquires its own lock and can't be called directly from `OnDebounceTimerElapsed`, which already holds `_solutionLock` when it reaches the reload branch (would deadlock), hence the fix duplicates the safe-swap pattern inline rather than delegating.

**Why this matters for future debugging**: if a workspace-loaded tool call ever reports implausibly massive, uniform reference-resolution errors (`CS0234`/`CS0246` on virtually every file) right after `GetWorkspaceHealth` claimed a clean load, check the server log around that time for "Reloading entire solution" / "Error refreshing workspace" — it may be [[project_operation_blob_json_gotchas]]-adjacent workspace corruption rather than a real code/reference problem. Also relevant: [[project_stale_server_before_rebuild]] if debugging this after the fix — rebuild bin-vscode before assuming the corruption can still happen.

**How to apply**: if similar "reuse existing long-lived resource, only reassign target field on the success line" patterns show up elsewhere in `PersistentWorkspaceManager.cs` (or other files managing `_workspace`), prefer the create-new/swap-only-on-success pattern already established by `ReloadWorkspaceFromDiskAsync` and this fix, rather than mutating in place across an `await` that can throw.
