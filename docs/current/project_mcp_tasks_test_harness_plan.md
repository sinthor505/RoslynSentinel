**Built and passing (2026-08-25, commit 565ad81):** `RoslynSentinel.Tests.Advanced\McpTasksHarnessTests.cs`, 4 tests, all green on first real run (~7s total). Confirms both the harness pattern itself and that MCP Tasks support (capability negotiation, response correctness, cancellation) all behave correctly. No test project exercised the MCP protocol layer end-to-end (client + server over real JSON-RPC) before this — existing tests either called tool classes directly (`SentinelAsyncifyToolsTests`) or built the DI graph without attaching a transport (`DependencyInjectionTests`). Task creation/`tasks/get`/`tasks/cancel` live entirely in the SDK's `CallToolWithAlternateFilters` dispatch layer, not in tool method bodies, so calling a tool class directly can never observe them — a real client/server pair was unavoidable. See [[project_mcp_tasks_support]].

`Features` (`RoslynSentinel.Server.Basic\SentinelWorkspaceTools.cs`) gained an optional `delaySeconds` param (`await Task.Delay(TimeSpan.FromSeconds(delaySeconds), cancellationToken)`, default 0 = no behavior change) and was added to `RoslynSentinelTaskTools.Names` — chosen over `BulkComment`/`Asyncify` per Andrew's call (2026-08-25) since it needs no solution loaded and no LLM dependency, isolating "does the harness work" from "does Tasks support work."

**The four tests, each proving one thing:**
- `PlainCall_ReturnsNormalResult_NoTaskInvolved` — baseline `CallToolAsync`, no task path at all.
- `TaskCapableClient_CallingTaskEligibleTool_ReturnsCreateTaskResult` — default `McpClientOptions.ProtocolVersion` (null) already negotiates `2026-07-28`, which is what makes `CallToolAsTaskAsync` return `CreateTaskResult` instead of a plain result. Confirmed from SDK source: capability injection is gated purely on negotiated protocol version, nothing else to configure client-side.
- `TaskCapableClient_PollingToCompletion_MatchesSynchronousResult` — `CallToolWithPollingAsync`'s result content matches a synchronous call with the same arguments, byte-for-byte via JSON serialization comparison.
- `CancelTask_MidFlight_StopsBeforeCompletionAndReportsCancelled` — cancels a 15s-delayed call after 2s, polls until `CancelledTaskResult`; whole test finishes in ~3s, proving the delay's cancellation token is actually observed rather than the work running to completion in the background regardless.

**Harness construction** (see the test file for full working code): two `System.IO.Pipelines.Pipe`s; server side is the real `AddRoslynSentinelEnginesAdvanced()` → `AddMcpServer().WithStreamServerTransport(...)` → `WithTasks(new InMemoryMcpTaskStore(), ...)` → `AddRoslynSentinelToolsAdvanced(services, activeModes)` with `activeModes = {"Workspace"}` (enough for `Features`). Registrations are built on a bare `ServiceCollection` (needed because `AddMcpServer()` takes `IServiceCollection`) then copied into a `Host.CreateApplicationBuilder()`'s `IServiceCollection` — required because running the hosted MCP server needs a real `IHost`/`RunAsync()`, not just `BuildServiceProvider()` (hosted services never start otherwise). `_host.RunAsync()` is fire-and-forget in `[SetUp]`. Client side is `ModelContextProtocol.Client.McpClient.CreateAsync(new StreamClientTransport(serverInput: clientWriteStream, serverOutput: serverReadStream, NullLoggerFactory.Instance))` with default `McpClientOptions`. `[TearDown]` disposes the client then stops/disposes the host — confirmed via `tasklist` that no processes leak after a run.

**Gotcha hit while building this:** `CallToolRequestParams.Arguments` is `IDictionary<string, JsonElement>`, not `IDictionary<string, object?>`. The convenience `client.CallToolAsync(string toolName, IReadOnlyDictionary<string, object>, ...)` overload accepts plain objects, but the `CallToolRequestParams`-based overload — required for `CallToolAsTaskAsync`/`CallToolWithPollingAsync`, which only take `CallToolRequestParams` — does not. Fixed with a small `ToArguments` helper using `JsonSerializer.SerializeToElement` per value.

**Side effect of adding `delaySeconds` to `Features`:** its signature changed from `object Features(...)` to `async Task<object> Features(...)`, which broke 4 call sites in `RoslynSentinel.Tests.Battery\BatteryTwentyTests.cs` that called it synchronously — fixed by making those test methods `async Task` and awaiting the call.

**Not yet done:** extending coverage to `Asyncify`/`AsyncifyLoop` — same harness pattern, ready to reuse.

**`BulkComment` extension (2026-08-26, commit 01867e1):** `RoslynSentinel.Tests.Advanced\McpTasksHarnessBulkCommentTests.cs`, 4 tests, all green. Same scaffolding as the `Features` fixture, but: `ActiveModes = {"Generation"}` (not `"Workspace"` — required for `SentinelCommentingTools`/`BulkComment` registration), a real `PersistentWorkspaceManager.LoadSolutionAsync` against [[project_test_asyncify]]-adjacent `RoslynSentinel.Tests\TestSolutionFixture.cs` (temp copy of `Samples\ContosoOrders`, real MSBuild open — not `SetTestSolution`, since the goal was full end-to-end fidelity including the real file watcher), and a new `FakeLlmClient` (`RoslynSentinel.Tests.Advanced\FakeLlmClient.cs`) registered via `services.AddSingleton<ILlmClient>(fake)` *after* `AddRoslynSentinelEnginesAdvanced()` — last registration wins, overriding the real `LmStudioClient` forwarding without needing to remove it. `FakeLlmClient.Delay` gives the cancellation test a controllable in-flight window, same trick as `Features`' `delaySeconds` but living in the fake client instead of the tool.

MCP tool JSON shape confirmed: `CallToolResult.Content[0].Text` parses to `{"success":bool,"data":{...},"hasMorePages":bool}` — the actual payload is one level deeper than `Features`' bare object, under `.data`, in camelCase.

**Real (non-dryRun) calls must scope to `project: "ContosoOrders.Core"`, not `scope: "solution"`.** Solution-wide real runs fail every member with "apply validation failed" — traced (see [[project_validation_engine_line_shift_bug]]) to a real latent bug in `ValidationEngine`'s diagnostic-delta dedup, triggered here because `ContosoOrders.Tests` (xUnit) has pre-existing unresolved-reference errors that `TestSolutionFixture` can never fix (it copies only `.sln/.csproj/.cs/.md`, no NuGet restore). Scoping the real-work tests to the one project that already compiles clean sidesteps it and matches how a realistic caller would invoke `BulkComment` anyway.
