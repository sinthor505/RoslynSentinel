Scope: `RoslynSentinel.Server.Basic/*.cs` + `RoslynSentinel.Server.Advanced/*.cs`, all `[McpServerTool]`
methods, per `C:\Users\Administrator\.claude\plans\shiny-wibbling-key.md`. These are issues noticed

## 1. `RunScanDetector` / `RequireProject` returns an error string instead of throwing

`RoslynSentinel.Server.Advanced/SentinelScanTools.cs:543-550`:

```csharp
private static string RequireProject(ToolScope scope, string? scopeName)
{
    if (scope != ToolScope.project || string.IsNullOrEmpty(scopeName))
    {
        return ("This detector requires scope='project' with a projectName as scopeName.");
    }
    return scopeName;
}
```

Called at line 313:

```csharp
var result61 = await _dependencyEngine.FindUnusedReferencesAsync(RequireProject(scope, scopeName));
```

When the precondition fails, `RequireProject` returns its own error message as if it were a valid
project name, and that string is passed straight into `FindUnusedReferencesAsync` — which will then
fail (or silently no-op) against a project named `"This detector requires scope='project' with a
projectName as scopeName."` instead of surfacing a clear `InvalidArgument` to the caller. Contrast
with `RequireFile` elsewhere in the same tool family, which throws `ArgumentException` on the same
class of precondition failure — `RequireProject` is the odd one out.

**Fix shape** (not applied — out of scope for this pass): change `RequireProject` to throw
`ArgumentException` like `RequireFile` does, or return a `Result`-style type the caller must check
before use.

## 2. `ApplyUnifiedDiff` "HEADER COUNT MISMATCH" — cosmetic, not a failure signal

Nearly every multi-hunk (and many single-hunk) `ApplyUnifiedDiff` call in this pass returned a
`diffHunkFindings` note like:

```
DiffHunkAnalyzer: 1 hunk(s).
  @@ -63,32 +63,25 @@ [HEADER COUNT MISMATCH: declared old=32/new=25, actual old=50/new=24 (context=14, -=10, +=10)]
```

This fires whenever the unified-diff hunk header's declared line counts don't match what the tool
actually parsed out of the hunk body (near-universal here, since diffs were hand-written rather than
generated by `diff`/`git diff`, so the `@@ -a,b +c,d @@` counts were rarely exact). It appears
alongside `"success": true` and `"validationResult": {"success": true, "diagnostics": []}` and has
never once corresponded to an actual problem in ~40 calls this pass — the tool re-anchors on content
and applies correctly regardless. Anyone reviewing transcripts should not read this note as an error;
it's worth either downgrading its visibility (info vs. warning-shaped) or, if the header counts are
truly unused for anything except this diagnostic, dropping the check.

## 3. `Member(add)` silently failed to persist twice, with no error, while reporting success

Discovered adding the `CodemodKind` enum to `RoslynSentinel.Common/ToolEnums.cs`
(`SentinelCodemodTools.cs`'s `Generate.kind`). Two consecutive `Member(operation: "add", ...)` calls
each returned:

```json
{"success": true, "data": {"summary": {"changeId": "...", "status": "applied",
  "note": "Written to disk. Call UndoLastApply(...) to revert if needed."},
  "changedContent": "...correct expected enum text..."}}
```

— full success shape, correct `changedContent`, a valid `changeId`, `workspaceInSync: true` — but a
subsequent `Grep` for `CodemodKind` in the target file found nothing, both times. Re-reading the file
directly confirmed it was byte-for-byte unchanged from before the call. This is a genuine silent
data-loss bug: the tool's own success contract (return shape + "written to disk" note) was violated
with no way to detect the failure short of independently re-reading the file. `UndoLastApply` on
either `changeId` was not attempted (no working state to undo), so it's unknown whether the changeId
itself was valid or fabricated.

**Workaround used**: switched to `ApplyUnifiedDiff` targeting the same insertion point, which applied
and persisted correctly on the first attempt. No repro isolated beyond "happened twice in a row for
the same target file/operation, and `ApplyUnifiedDiff` didn't reproduce it for the same file
immediately after." Given the blocking-error policy, this is the highest-severity item in this doc —
worth its own investigation before `Member(add)` is trusted for unattended sequences again.

## 4. Class-of-bug note: pre-existing test call sites masked by loose assertions

Not a currently-unfixed item (all instances found this pass — `MoveAllTypesToFiles`, `SyncInterface`,
`Inline` call sites in `BatteryTwentyFourTests.cs`, `BlobIntegrityInvariantTests.cs`, and
`BugFixTests.cs` — were fixed as a necessary side effect of the enum conversions that exposed them),
but worth flagging as a pattern for a broader audit: several test call sites omitted the `reason:`
named-argument label on a method whose first two parameters are similarly-typed, shifting every
subsequent positional argument one slot early. Each one silently landed in the tool's fallback
"Unknown X" error path, and passed anyway because the assertion was a loose
`Assert.That(result, Is.Not.Null)` rather than checking `Success`. The ones surfaced by this pass are
fixed; there may be others in call sites that happen not to run through a parameter this pass touched.

## 5. `WrapRange.wrapper` — schema reports optional, but is actually always required

Already flagged in-code at `SentinelAdvancedRefactoringTools.cs` (`WrapRange`) via:

```
// TOOL-OPTION-REQUIRED-FLAG-STALE: wrapper carries a C# default ("") purely so it can stay after
// startLine/endLine in parameter order (existing positional call sites depend on this order); it is
// actually unconditionally required — the body always falls through to an "Unknown wrapper" error
// when it doesn't match tryCatch/using/region. The schema wrongly reports it optional.
```

Noted here only for completeness since it's the one `TOOL-OPTION-REQUIRED-FLAG-STALE` marker from
this pass — no separate action needed beyond what the marker already documents. Real fix requires
reordering `WrapRange`'s parameters (breaking existing positional call sites) or restructuring the
tool, both out of scope for this pass.
