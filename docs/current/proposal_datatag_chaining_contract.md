# Activating the DataTag attribute convention as a tool-chaining contract

Companion to `docs/current/proposal_structuredcontent_rollout.md` (same session). That proposal is
about advertising a tool's *output shape*; this one is about advertising which *fields* of that
output are meant to feed which *parameters* of other tools. Each stands alone.

## Origin and framing

RoslynSentinel's MCP tool parameters already carry a set of attributes - `[Produces]`, `[Consumes]`,
`[ExternalInputRequired]`, `[ToolOption]` - built around a `DataTag` enum (66 semantic field-name
values: `SymbolName`, `SourceFilepath`, `ChangeId`, `MemberName`, `ContainerName`, etc., defined in
`RoslynSentinel.Common/DataTag.cs`). These were applied by hand, one parameter at a time, across
hundreds of tool parameters over time.

Per the project owner directly: these attributes were originally applied purely for **human
documentation and organization** - an attempt to manage the sheer number of parameters across
RoslynSentinel's tool surface and bring order to it, predating any plan to use them with an AI model
or make them do anything at runtime. This proposal is **not** a resumption of an abandoned
automation effort. It is a proposal to formalize and activate a documentation convention that
already has real design discipline behind it - the audit below finds several tool classes
completely clean and correctly tagged. The remaining work is comparatively mechanical (reflection +
exposure), not "invent what the categories should mean" - that part is already decided and
mostly-correctly applied. Read this as capturing value that was already paid for, not building new
infrastructure from scratch.

Also directly from the project owner, and load-bearing for how the audit findings below should be
read: every application of `[Consumes]`/`[ExternalInputRequired]`/`[Produces]`/`[ToolOption]` to
date was added **manually**. None of it was ever generated by an AI agent authoring a tool file,
because carrying the convention forward was never stated as a requirement for new code. This
directly explains the shape of the coverage-gap findings below (`SentinelGitTools`,
`SentinelAsyncifyTools`, `SentinelCommentingTools`): those files are not neglected or decayed, they
are files nobody was told to tag. That is a process/requirements gap, not a quality regression, and
the proposal in "What this doc proposes" below addresses it as such.

## The intended design (authoritative - given directly by the project owner, not inferred)

1. `[Produces(DataTag.X)]` on a **tool method** - the DataTag(s) that tool's output/response
   contains.
2. `[Consumes(DataTag.X, required: bool)]` on a **parameter** - the parameter takes a value of
   DataTag X that plausibly comes from another tool's output: a "chained" value, something
   obtainable by calling `LocateSymbol`/`GetFileOutline`/`GetMethodSource`/etc. first (e.g. a
   filepath, an existing symbol/member/class name being looked up, source code read then passed
   back, a baseline object produced by an earlier scan call).
3. `[ExternalInputRequired(DataTag.X, required: bool)]` on a **parameter** - a "judgment"/free-hand
   value with no canonical producer tool. Two sub-flavors: (a) disambiguation context the model
   transcribes by reading code itself (`contextSnippet`, `lineBefore`, `lineAfter`, `oldContent`,
   `newContent`); (b) a new value the model is authoring/deciding, not looking up (a new
   member/type/namespace name being created, a modifier keyword to add, an accessibility level, a
   boolean flag).
4. `[ToolOption(ToolOptionTag.X)]` on a **parameter** - a non-data tuning/behavior knob that affects
   the tool but isn't itself a data value being passed through (`autoStage`, `dryRun`, `limit`,
   `returnDiff`, `validateOnApply`, and - per the audit below - also mode/behavior-selector enums
   like an operation-kind chooser).

The key thing to hold onto: the `DataTag` **value** alone never determines the correct attribute -
the parameter's **role** does. Worked example, `Member`
(`RoslynSentinel.Server.Basic/SentinelRefactoringTools.cs:591` and `:601` vs. `:589` and `:593`):
`namespaceName` and `typedName` are correctly `[ExternalInputRequired(DataTag.SymbolName)]` because
they name something being newly authored, sitting right alongside `memberName` and `containerName`,
correctly `[Consumes(DataTag.SymbolName)]`, because they look up something that already exists.
Same `DataTag.SymbolName` value, opposite attribute, both correct - role (lookup vs. authorship)
decided it, not the tag.

## Current state - what's real vs. inert

Verified directly this session, not carried over from a prior pass:

- `[Consumes(` and `[ExternalInputRequired(` are both extremely widely applied: 173 and 130 literal
  matches respectively (`SearchSolutionText`). This was re-verified twice independently this session
  after an initial subagent wrongly claimed `Consumes` was unused entirely - noted here as a caution
  that every claim in this doc was directly re-checked via tool calls against source, not carried
  over from a single earlier pass.
- Neither `ConsumesAttribute` nor `ExternalInputRequiredAttribute`
  (`RoslynSentinel.Common/ConsumesAttribute.cs`, `RoslynSentinel.Common/ExternalInputRequiredAttribute.cs`)
  carries any XML doc comment explaining this distinction - confirmed by direct `ReadFile` of both
  files in full. The 4-way meaning above exists only as an unwritten convention across call sites.
- `[Produces]` **is** read at runtime.
  `RoslynSentinel.Server.Advanced/ServiceRegistrationExtensionsAdvanced.cs`'s `BuildToolGraph`
  method (called at line 75, defined from line 84) reflects `[Produces]` off tool methods
  (`method.GetCustomAttributes<ProducesAttribute>()`, line 124) and builds a `ToolGraph`
  (`RoslynSentinel.Common/ToolGraph.cs`, `Build`/`ProducersOf` at lines 38-89). But this is scoped to
  exactly one tool class - `BuildToolGraph(new[] { typeof(SentinelAsyncifyTools) })`,
  `ServiceRegistrationExtensionsAdvanced.cs:75` - and its only consumer is `FailureRouter.Route`
  (`RoslynSentinel.Common/FailureRouter.cs:27`), used reactively to prefill a `ToolHint` after one
  specific async-migration failure type. It never touches schemas or a tool's advertised
  `[Description]` text.
- `[Consumes]` has **zero** reflection reads anywhere in the solution. Confirmed:
  `SearchSolutionText` for `ConsumesAttribute` returns only the class's own declaration and
  constructor (`ConsumesAttribute.cs:4` and `:11`); a follow-up search for
  `GetCustomAttribute<Consumes` returns zero matches solution-wide.
- `ToolGraph`'s consumer-side index (`_consumersByTag`) is permanently null - `ToolGraph.Build`
  (`ToolGraph.cs:38-67`) always constructs `new ToolGraph(null, producers)` (line 66), never
  populating the first argument. The two methods that would read it,
  `ToolHints.OnSuccess`/`ToolHints.OnMissingInput` (`ToolGraph.cs:114-124`), are literal
  unimplemented stubs: `// TODO: implement using ConsumersOf once consumer index is populated` /
  `// TODO: implement using ProducersOf once callers are migrated to DataTag-keyed lookup`, and both
  unconditionally `return null`.
- Nothing surfaces `DataTag`/`Produces`/`Consumes` information into a tool's advertised
  `[Description]` text or MCP schema today - it is purely internal/inert metadata as far as the
  model or MCP client can see.
- The `DataTag` enum itself (`DataTag.cs:3-71`) has a gap relevant to the very use case that
  motivated this investigation: there is no `DocCommentId` value, even though `docCommentId` is a
  real field name threaded through `LocateSymbol`'s output and consumed by `RenameSymbol`/
  `PreviewRenameImpact`/etc. (`SentinelRefactoringTools.cs:457` and others). The closest existing
  tags are `SymbolId`/`SymbolHandle`/`SymbolName`, none of which is actually the field. This gap
  blocks the exact chaining example that originally motivated this investigation - `LocateSymbol`'s
  `docCommentId` output feeding `Member`'s `docCommentId` input - from being representable at all
  under the current enum. Flagged as a concrete extension needed before that use case can work.
- Separately, `DataTag.cs:67` has a typo: `ChangeseFormat`, not `ChangesetFormat`. Noted here, fixed
  alongside the drift pass below.

## Drift audit findings

Sampled 11 previously-unaudited tool classes (`SentinelSymbolTools`, `SentinelWholeFileWriteTools`,
`SentinelGitTools`, `SentinelCodemodTools`, `SentinelGenerationTools`, `SentinelIntelligenceTools`,
`SentinelQualityTools`, `SentinelScanTools`, `SentinelAsyncifyTools`, `SentinelModernizationTools`,
`SentinelCommentingTools`), ~28 tool methods, 95+ parameters, via direct `GetMethodSource` reads
against the 4-way design above. This was done **after** the project owner explained the intended
design - the audit checked real usage against the authoritative definition above, not a guess at
what the categories should mean.

A useful lens while reading these, not a strict bucketing: some findings are miscategorizations
that are wrong under a pure-documentation reading too - a wrong tag is a wrong tag whether or not
anything reads it at runtime. Others are ambiguous-but-harmless as a human-legible comment (a
maintainer skimming the code could still tell what was meant) and would only break a deterministic,
reflection-driven mechanism if left as-is. Total absence of any tag gives a human reader nothing
either, so most findings below are drift by either standard - but it's worth keeping this
distinction in mind per finding rather than forcing everything into one bucket.

Also directly from the project owner, and important for how Pattern 1 below should be read:
`ExternalInputRequired` is over-represented in the audit relative to its actual intended meaning
because it doubled as an implicit default - "this parameter needs a value, but I haven't
identified/confirmed where that value's source is" - rather than every application being a
considered claim that the value is genuinely a judgment/free-hand input. That reframes Pattern 1's
findings: they are less "the wrong tag was deliberately chosen" and more "a provisional placeholder
was never revisited." Practically, this means a cleanup pass should treat every existing
`ExternalInputRequired` site as provisional and re-derive the correct tag from the parameter's
actual role, rather than assuming it's correct unless a specific contradiction turns up.

### Pattern 1: existing-lookup value tagged ExternalInputRequired instead of Consumes

Per the "unresolved default" note above, treat every finding in this pattern as a provisional tag
that was never revisited, not a deliberate misjudgment.

- `SentinelSymbolTools.cs` `LocateSymbol` ~line 78: `symbolName` tagged
  `[ExternalInputRequired(DataTag.SymbolName, required: true)]` - wrong, it's a lookup key for an
  existing declared symbol (the tool's entire purpose). Contrast: `FindReferences`'s `symbolName`
  (~line 404) correctly uses `[Consumes(DataTag.SymbolName, required: true)]`. Should be `Consumes`.
- `SentinelSymbolTools.cs` `LocateSymbol` ~line 84: `projectName` tagged
  `[ExternalInputRequired(DataTag.ProjectName)]` - inconsistent with `QuerySymbolRelationships`/
  `GetTypeInfo`/`GetDiRegistrations`/`GetPublicApiSurface`, which all correctly tag `projectName` as
  `Consumes` (read off prior `ListSolutionItems`/`GetSolutionMetrics` output). Should be `Consumes`.
- `SentinelSymbolTools.cs` `LocateSymbol` ~line 85: `filepath` tagged
  `[ExternalInputRequired(DataTag.SourceFilepath, required: false)]` - `filepath` is canonically
  `Consumes` everywhere else (`InspectSymbol`, `FindReferences`, dozens more). Should be `Consumes`.
- `SentinelSymbolTools.cs` `QuerySymbolRelationships` ~line 229: `name` tagged
  `[ExternalInputRequired(DataTag.SymbolName, required: true)]` - same drift, a lookup key for an
  existing type/interface/attribute. Should be `Consumes`.
- `SentinelGenerationTools.cs` `GenerateHttpClient` ~line 61: `controllerName` tagged
  `[ExternalInputRequired(DataTag.ClassName)]` - names an existing controller class looked up in
  `filepath` (the error path literally says `"controller class '{controllerName}' not found"`), not
  an authored name. Contrast: `GenerateClassesFromJson`'s `rootClassName` correctly uses
  `ExternalInputRequired` because that name **is** brand-new. Should be `Consumes`.
- `SentinelCodemodTools.cs` `ApplyMethodCodemod` ~lines 392-403: `methodName` tagged
  `[ExternalInputRequired(DataTag.MethodName, required: true)]` - every transform branch looks up an
  existing method, erroring `"method not found... use GetFileOutline to verify"` if absent - a
  lookup key, not an authored value. Contrast: `GetMethodComplexity`/`GetTestCoverageMap`/
  `GetCallGraph`/`InvertBooleanLogic` all correctly use
  `[Consumes(DataTag.SymbolName, required: true)]` for the equivalent parameter. Should be
  `Consumes`.

### Pattern 2: mode/behavior-selector flag tagged as data instead of ToolOption

- `SentinelWholeFileWriteTools.cs` `ApplyDiff:298`: `changesetFormat` (files/diff mode selector)
  tagged `[ExternalInputRequired(DataTag.ChangeseFormat)]` (note the enum's own typo, "Changese" not
  "Changeset" - flagged above as a small separate fix). This is a mode selector, exactly like
  `InspectSymbol`'s `aspect` or `GetTypeInfo`'s `include` (both correctly `ToolOption` elsewhere).
  Should be `ToolOption`.
- `SentinelWholeFileWriteTools.cs` `ApplyDiff` and `ApplyUnifiedDiff`: `action` (apply/validate
  toggle) in both, tagged `[ExternalInputRequired(DataTag.Action)]` - the exact kind of mode flag
  the design's own `dryRun` example calls `ToolOption`. Should likely be `ToolOption` in both.
- `SentinelScanTools.cs` `RunScanDetector`: `detector` (a `DetectorId` enum choosing which analysis
  to run) tagged `[Consumes(DataTag.DetectorName)]` - a mode-selector enum like `aspect`/`include`/
  `direction` (all correctly `ToolOption` elsewhere); nothing actually "produces" a chainable
  `DetectorName` value for this to consume (`DescribeScanDetectors` documents valid ids in
  prose/JSON, not as a chainable handle). Should be `ToolOption`.
- `SentinelScanTools.cs` `RunScanDetector`: `scope` (`ToolScope`: file/project/solution) tagged
  `[ExternalInputRequired(DataTag.Scope)]` - same class of drift, a tuning/mode selector, not a
  freehand judgment value. Should be `ToolOption`.
- `SentinelCodemodTools.cs` `ApplyMethodCodemod`: `transform` (free-text string selecting 1 of 17
  hardcoded transform kinds via switch) tagged `[ExternalInputRequired(DataTag.Transform)]` - same
  mode-selector drift. Should be `ToolOption`. Separately, and out of scope for the attribute-tag
  fix itself: being a free-text string rather than an enum means the schema can't constrain it to
  valid values either - worth a follow-up on its own.

### Other specific miscategorization

- `SentinelWholeFileWriteTools.cs` `ApplyDiff:302`: `changes` (a `Dictionary<string,string>` of
  filepath -> new content) tagged `[ExternalInputRequired(DataTag.OperationId)]` - doubly wrong:
  `DataTag.OperationId` is semantically unrelated to file-content payloads (reads like a copy-paste
  of the wrong enum value), and the parameter is really new/edited file content, not an operation
  identifier.
- `SentinelScanTools.cs` `ScanBreakingChanges:718`: `baseline` tagged
  `[ExternalInputRequired(DataTag.ApiBaseline)]`, but per its own description is literally "the
  baseline list returned by `GetPublicApiSurface(persistBaseline: true)`" - a textbook chained
  value. Should be `[Consumes(DataTag.ApiBaseline, required: true)]`. Related defect, and worth
  calling out separately since `Produces` is the one attribute already read at runtime:
  `ScanBreakingChanges` itself declares `[Produces(DataTag.ApiBaseline)]` on the method
  (`SentinelScanTools.cs:713`), which is backwards - it consumes a baseline, it doesn't produce one.
  The actual producer, `GetPublicApiSurface` (`SentinelScanTools.cs:785`), only declares
  `[Produces(DataTag.Report)]`, not `DataTag.ApiBaseline`. This is a `Produces`-side
  miscategorization, not just a `Consumes`-side one.

### required:true/false vs. actual nullability mismatch

- `SentinelScanTools.cs` `GetPublicApiSurface` ~line 789: `projectName` (nullable `string?`, default
  `null`) tagged `[Consumes(DataTag.ProjectName, required: true)]` - `required: true` contradicts
  the parameter's own nullability; the tool's own doc / a `CONDITIONAL-PARAM-REVIEW-REQUIRED`
  comment says it's only required when `persistBaseline=false`, i.e. conditionally required, not
  unconditionally. Should be `required: false`, with the condition left to description/runtime
  check, matching the pattern used for other genuinely-conditional params elsewhere (see
  `docs/current/issue_member_containername_conditional_required_gap.md` and its linked
  `issue_conditional_required_param_audit_followup.md` for the same shape of gap on a different
  axis - the attribute model has no "required when X" construct at all).

### Coverage gaps - total absence of tagging, not miscategorization

Per the framing above: these are files nobody was told to tag, not files that decayed after being
tagged.

- `SentinelGitTools.cs` `Git` method: all 16 non-`reason` parameters (`operation`, `count`,
  `target`, `paths`, `maxBytes`, `message`, `scope`, `files`, `commitHash`, `noCommit`,
  `branchName`, `startPoint`, `deleteBranch`, `createBranch`, `remoteName`, `setUpstream`, `amend`)
  carry none of `Consumes`/`ExternalInputRequired`/`ToolOption`. Total gap across an entire tool.
  Under the design: `commitHash` should be `Consumes` (typically read from a prior log call);
  `message`/`branchName`/`startPoint`/`remoteName` should be `ExternalInputRequired` (authored
  values); `operation`/`count`/`maxBytes`/`scope`/`noCommit`/`deleteBranch`/`createBranch`/
  `setUpstream`/`amend` should be `ToolOption`.
- `SentinelAsyncifyTools.cs` (largest gap found - ~3684 lines, ~35 tool methods):
  `ScanAsyncMigrationCandidates` has 8 of 10 non-`reason` params (`scope`, `projectName`,
  `filePath`, `pattern`, `summarize`, `topN`, `minScore`, `forceRescan`) completely undecorated.
  `BridgeAsyncMethods`'s `targets` (a `List<BatchTarget>` of existing file/method pairs, explicitly
  chained from `ScanAsyncMigrationCandidates` output per the tool's own description - the clearest
  possible `Consumes` case in the whole sample) is undecorated entirely; `dryRun`/`maxItems`/
  `propagateCancellationTokens` also undecorated. `AddCancellationToken` shows the same gap pattern
  (`targets` should be `Consumes`, `dryRun`/`maxItems` should be `ToolOption`). Reads as a
  whole-file gap - the file was never in scope for the original hand-applied tagging pass - rather
  than isolated misses.
- `SentinelCommentingTools.cs` `BulkComment`: `scope`, `projectName`, `filePath`, `dryRun`,
  `maxMembers`, `maxRuntimeSeconds` all undecorated - same wholesale-gap pattern as Asyncify.
  `projectName`/`filePath` should be `Consumes`; `scope`/`dryRun`/`maxMembers`/`maxRuntimeSeconds`
  should be `ToolOption`.

### Clean files - reported explicitly, not a non-finding

- `SentinelIntelligenceTools.cs` - no drift found (`GetCallGraph`, `PreviewMoveFileToNamespaceFolder`,
  `TraceVariableLifetime`, `GetDiRegistrations` all correctly separate `Consumes` from `ToolOption`).
- `SentinelQualityTools.cs` - no drift found (`GetMethodComplexity`, `GetTestCoverageMap`,
  `AnalyzeSwitchForPatternConversion` all correct).
- `SentinelModernizationTools.cs` - no drift found (`InvertBooleanLogic` correct; small file, thin
  sample, noted as a caveat).
- `SentinelCodemodTools.cs`'s `lockFieldName` param (default `"_lock"`, a new lock-object field
  name) correctly tagged `[ExternalInputRequired(DataTag.SymbolName)]` - noted for contrast as a
  correctly-applied authored-value case, not a finding.

### Overall characterization

Out of roughly 95+ parameters checked across 11 files, about 20 concrete findings were logged
(excluding the deliberately-correct contrast case). Drift clusters into two distinct failure modes:
(1) miscategorization - an existing-lookup key tagged `ExternalInputRequired` instead of `Consumes`
(recurring across `LocateSymbol`, `QuerySymbolRelationships`, `GenerateHttpClient`,
`ApplyMethodCodemod`), and a mode/behavior-selector flag tagged as data instead of `ToolOption`
(recurring across `ApplyDiff`, `RunScanDetector`, `ApplyMethodCodemod`); (2) coverage gaps - three
files (`SentinelGitTools`, `SentinelAsyncifyTools`, `SentinelCommentingTools`) show near-total
absence of tagging, consistent with never having been touched by the original hand-applied pass,
rather than isolated mistakes. Three files (`SentinelIntelligenceTools`, `SentinelQualityTools`,
`SentinelModernizationTools`) were completely clean. Characterize overall drift as "pervasive but
unevenly distributed" - several files exemplary, several files never tagged at all - rather than
either "rare" or "uniformly bad."

## What this doc proposes

The following is a recommendation, for the reader to accept or reorder - only the design definition
(the 4-way meaning) and the audit findings above are established facts from this session.

1. **Fix the drift** (the miscategorization findings above) as a prerequisite cleanup pass, file by
   file - cheap, since it's attribute-argument edits, not logic changes, but it must happen before
   any reflection-driven mechanism can be trusted. A reflection reader built today would faithfully
   propagate every miscategorization and gap found above.
2. **Fill the coverage gaps** (`SentinelGitTools`, `SentinelAsyncifyTools`,
   `SentinelCommentingTools`) as part of the same pass, tool class by tool class - this is the
   larger share of the work by parameter count.
3. **Extend `DataTag`** for known-missing values, `DocCommentId` at minimum, given it's the
   motivating example for this entire investigation. Audit for other gaps opportunistically during
   the drift-fix pass rather than trying to enumerate every missing value up front.
4. **Fix the `Produces`-side miscategorization** on `ScanBreakingChanges` (declares
   `Produces(ApiBaseline)` when it should declare `Consumes(ApiBaseline)`; `GetPublicApiSurface`
   should probably declare `Produces(ApiBaseline)` instead of, or in addition to, `Produces(Report)`)
   as part of the same cleanup, since `Produces` is the one attribute already live at runtime.
5. **Make tagging a stated requirement going forward**, not just a backlog cleanup. Per the
   provenance note above, every application of these attributes to date was manual, and applying
   them was never stated as a requirement for new tool code - human or AI-authored. Without an
   explicit requirement, the same gap reopens on the next tool file added, the same way
   `SentinelGitTools`/`SentinelAsyncifyTools`/`SentinelCommentingTools` opened. Where to state and
   enforce this is itself open: candidates include adding a line to `CLAUDE.md`'s working
   conventions, a review checklist item, or a hook (of the same kind as
   `.claude/hooks/enforce-dogfood.ps1`) that checks new/modified tool parameters for missing tags -
   though whether a hook can reliably tell "correctly tagged" from "tagged with something" is itself
   an open question, since the harder miscategorization findings above (role vs. tag value) are not
   mechanically checkable by presence alone. This is a recommendation to weigh, not a decision.
6. **Then** - not before - build the actual mechanism: populate `ToolGraph`'s consumer index by
   reflecting `Consumes` (or `ExternalInputRequired`, or both) the same way `BuildToolGraph` already
   reflects `Produces`; widen `BuildToolGraph`'s scope from one tool class
   (`SentinelAsyncifyTools`) to the whole tool surface; and decide an exposure mechanism. This last
   part is a genuinely open question with at least two options worth weighing against each other,
   not resolved here:
   - (a) surface producer/consumer `DataTag` pairings via `CallToolResult`/`OutputSchema`-adjacent
     metadata, so the pairing is visible to the model at schema-inspection time, before either tool
     is called; or
   - (b) a response-envelope field naming what `DataTag` the returned data represents - weaker,
     because it only teaches the model the pairing reactively, after it has already called the
     producer once.

**Cross-reference:** this proposal's step 6 (widening `BuildToolGraph`, populating the consumer
index) is a natural complement to `proposal_structuredcontent_rollout.md`'s schema-attachment work -
a tool's `OutputSchemaType` and its `Produces`-derived `DataTag` list describe overlapping but not
identical information (`OutputSchemaType` describes the full shape; `DataTag` names the semantic
field), so both could reference the same underlying named DTOs once those exist. Noted here for a
future reader, not developed further - not a decision point in this doc.

**Concrete synergy, verified feasible this session:** once a tool's output DTO exists as a real named
type (the prerequisite from `proposal_structuredcontent_rollout.md`), `[Produces]` could move from
method-level ("this tool's output contains a `ChangeId` *somewhere*") to **property-level** on that
DTO ("*this specific property* is the `ChangeId`") - closing the gap where `[Produces]` today can
name a `DataTag` the output contains but never which field holds it. This is mechanically confirmed,
not speculative:
- `ProducesAttribute`'s `[AttributeUsage]` (`RoslynSentinel.Common/ProducesAttribute.cs:3`) allows
  only `Method | Parameter` today - adding `Property` is a one-line change.
- The MCP SDK's schema generator does not natively read `[Produces]` (it only special-cases
  `[Description]`, at one call site in `Microsoft.Extensions.AI.Abstractions`), but it exposes
  exactly the extension point needed: `AIJsonSchemaCreateOptions.TransformSchemaNode`, a callback
  that can reflect arbitrary attributes off each generated schema node via
  `ctx.GetCustomAttribute<TAttribute>()`.
- RoslynSentinel already has a **live, production callback wired into that exact hook**:
  `McpToolSchemaFix.cs`'s `RewriteBrokenSchemaNode` (`McpToolSchemaFix.cs:41-67`), already threaded
  through every tool via `WithToolsFixed<T>` (`McpToolSchemaFix.cs:73-103`). It currently patches
  broken `true`/missing-`type` schema nodes for a different bug; extending it with one more branch -
  check for `[Produces]` on the DTO property, inject the `DataTag` into that property's schema node
  as a vendor-extension key (e.g. `"x-produces-tag"`, since JSON Schema permits free-form keys and
  the SDK reserves none of its own for this) - reuses infrastructure already running in production,
  rather than requiring new plumbing or any SDK change.

This depends on the DTO work in `proposal_structuredcontent_rollout.md` landing first: property-level
`[Produces]` needs a real named property to decorate, which only exists once a tool's `Data` moves
off `object` onto a concrete type. Recorded here as a concrete extension of step 6, not a new
independent proposal.

## Cost / risk

- Steps 1-4 touch only attribute arguments on existing parameters/methods - no logic changes, no
  behavior changes, low risk. The risk is entirely in getting each individual tag *right*, which is
  a judgment call per parameter (see the worked `Member` example above) rather than a mechanical
  find-and-replace. Because `ExternalInputRequired` doubled as an implicit "unconfirmed" default
  (see Pattern 1 above), every existing `ExternalInputRequired` site should be treated as
  provisional during the pass, not just the ones already flagged - the audit sampled 11 of the
  solution's tool classes, not all of them, so more provisional sites likely exist outside the
  sample.
- Step 5 (making tagging a stated requirement) has no code cost but a process cost: it is one more
  thing to check on every new or modified tool method, and - per the open question above - may not
  be mechanically enforceable to the same standard the drift audit applied by hand.
- Step 6 (the actual mechanism) is the only step that changes runtime behavior. Widening
  `BuildToolGraph` beyond `SentinelAsyncifyTools` means every tool method now participates in
  `FailureRouter`'s hint-selection logic, which has only been exercised against one tool class to
  date - worth a small spike against a second tool class before committing to solution-wide
  reflection.
- Doing step 6 before steps 1-4 would make the mechanism actively misleading rather than merely
  incomplete: it would confidently point the model at a wrong producer/consumer pairing wherever the
  audit above found drift, which is worse than the current all-inert state.
